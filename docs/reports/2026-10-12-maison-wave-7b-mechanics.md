What exists: a verifier-proposed one-criterion swap (`steps.py:3166` `swap_pair`, applied by `steps.py swap`; the rule is `plugins/sdlc-lite/agents/verifier.md:37`), in 0.22.4; a bounded multi-token correction is design only, token-fix only, unbuilt (`docs/specs/sdlc-lite/bounded-plan-correction.md:3`); anything larger is /chain 4.2 (move the step dir to `step-<n>.superseded-<k>`, replan, split). Smallest mechanical change: a `steps.py lint` warning `history-shaped criterion` for a criterion span that counts or greps commit subjects (`git log`, `git rev-list --count`, `grep -c` on `--oneline` output), so the plan reviewer sees it before a builder does. Red check: a `steps.py selftest` lint case with `- \`git log --oneline $SDLC_BASE_SHA..HEAD | grep -c 'feat: x' | grep -qx 3\`` that today lints clean (exit 0, no finding). What is still missing: `Verdict` must read `fail` beside a held line (`results.py:254-257`, by schema) and `tickets.py close` refuses any held criterion (`tickets.py:1963-1966`), so a ticket with every criterion met except one properly deferred to a stage cannot close (the fleet retro row 1 question, `docs/reports/2026-10-12-fleet-retro-00.md:20`). 5. Silent running agent is invisible. Confirmed. `attempt_state` reads `running` until the parent pid is dead or reused (`dispatch.py:463-471`); nothing reads the transcript's age. The transcript path is known only by agent id (`dispatch.py:1009`), and the attempt gets `agent_id` only at `record` (`dispatch.py:1055`), so a status-time check has no id to look with. Smallest change is therefore two pieces: `dispatch.py started <dispatch.json> --agent-id ID` writes the id into the running attempt at spawn, and `status` prints `last activity <age>` from the transcript mtime, with `silent` once it passes a threshold (30 min). Red check: a `dispatch.py selftest` case with a running attempt, a stored id and a fake `subagents/agent-<id>.jsonl` dated 2 h back: today `status` prints `running` and nothing else. Maison's cost: one 2.5 h wait.
6. Resumed work trips the red checkpoint. Confirmed, and the mechanism is narrower than the finding says. A control binds to its criterion key and its `base_sha` (`redck.py:213-214`), and the audit reads only the step dir's own `red-checkpoint.jsonl` (`redck.py:56`, `redck.py:182`). The phase is `pre-edit` only when nothing differs from the base (`redck.py:176`); a second builder on a branch that already holds the first builder's commits is `retrospective` at its first control, and `preserved` only when an earlier attempt in the same dir recorded a pre-edit red at the same base (`redck.py:222-226`). Maison's `step-1/process-deviations.md:2-5` shows four attempts, each with a different handoff sha256, read `retrospective, missing, retrospective, retrospective`; `step-1.superseded-1/process-deviations.md:2` is `retrospective` too, so no attempt of either dir ever held a pre-edit red (an integration step goes green by merging commits that already exist, so the first builder was already past the base when it ran `redck record`) `[U]` on the exact dirty paths. T-0425 (0.22.3) covers a handoff edit, not a moved base or a superseded dir. Smallest change, three rules: `redck record` reads the phase against the working tree (no uncommitted source change, `git status --porcelain` on the source paths) and stores the commit it ran at; `redck audit` binds a control whose `base_sha` is the current base or an ancestor of HEAD, and still refuses a different lineage; and an own pre-edit control that is green defers to an earlier same-lineage pre-edit red before it reads `green-baseline`, else `preserved` is unreachable on a resumed build. Red check, two cases in `redck.py selftest` after the resumed-work case (`redck.py:373-379`): (a) base kept at the first dispatch (a rework keeps it), the A1 work committed, `record --attempt-id A3`: today `retrospective`, want `pre-edit`; (b) base moved to HEAD and no A3 control, `audit --attempt-id A3`: today `missing` (the control at `redck.py:390-394`), want `preserved`.
7. Gate lock. Partly confirmed. Legacy slot files are read only and charged the default need, 3 of 6 compute units each (`gate_lock.py:414-436`, `gate_lock.py:65`, `gate_lock.py:617`), but only while their pid is alive with the recorded start (`gate_lock.py:107-111`), so a dead 0.22.1 holder costs nothing; an expiry for a live one would kill a running gate and is refused here. Per-repo fairness exists: round robin among the repos at the top priority (`gate_lock.py:24-26`, `gate_lock.py:377-383`), and `--priority` is already a flag. The missing piece is the ETA: `status` prints `age_s` and `waited_s` only (`gate_lock.py:712-726`). T-0456 on main lets a cheap gate declare a small weight (`fanout.py:10` `--gate-need`) and reports a lock timeout as not run, never red; that is the larger share of the 70 min wait and is unreleased. Smallest change left: `status` adds, per queued row, `ahead` (compute units held plus queued before it) and `blocking` (the names), so a conductor can decide to wait or cancel. Red check: a `gate_lock.py selftest` status case asserting the two keys; absent today.
8. `fanout.py` cannot run with a gitignored `.sdlc`.
