# Merge ops and the merge queue

Design from the T-0488 architect pass (2026-10-12). Not built. Recommendation: a merge queue as the existing integration branch plus a forward-merging `settle`; merge-ops as a conductor duty block backed by scripts; no blanket worktree-per-builder rule.

<!-- role=architect level=L1 model=fable effort=high -->
### Approach

The six questions, each with its answer from the code and this session's records. Every `fanout.py` line below was read on main at `abfe262b`; the light-merge design's line numbers are stale by about 20 lines and are not reused.

(1) What exists, and who does each job. The merge path is already a queue in all but name, inside one wave: `fanout.py land` takes one finished branch through `merge_gate_close` (`plugins/sdlc-lite/scripts/fanout.py:1421`), which waits for planned-scope overlap outside the lock (`wait_for_overlap`, `:1390`, `:1429`), then under an exclusive `fcntl.flock` on `<lanes-dir>/merge.lock` (`:1145`) records the merged paths (`:1438-1440`), merges `--no-ff` as `Merge <branch>: <id>` (`:1442`), runs every `--gate` through `gate_lock.py` with one retry after a lock timeout (`:1455-1476`, T-0456), resets a red merge (`:1483`), closes the ticket and commits `close <id>` (`:1494-1518`). The lock is held from `:1430` to `:1519`, so the gates of one land block every other land into that integration branch; a `merge conflict` outcome (`:1448`) is handed back to the sub-agent by name to merge the integration branch on its side (fanout `SKILL.md:30`). `roll` (`:2372`) is the fast path for a `rolling` lane straight onto main, ff only. `settle` (`:2330`) fast-forwards main to the integration branch and closes the tree; a diverged branch is refused with exit 2 and left whole (`:2343-2347`). `gate_lock.py` is the machine-wide weighted FIFO admission queue across repos (its docstring, `DEFAULT_TIMEOUT = 1800.0` at `gate_lock.py:63`); `lanes.py` owns open, close, sweep and the landed test, and `sweep --apply` runs at `fanout.py run` and `prep` start and by hand after settle (fanout `SKILL.md:16`, `:51`). The conductor's duties today are lines of prose: close and merge in the same turn, then the lane sweep (`agents/conductor.md:9`); route parallel tickets to `/fanout` (`:20`); publishing only after AskUserQuestion (`:47`); heavy gates through `gate_lock.py`, `--priority N` for a job that blocks an integration (`:58`). The maintainer does by hand: the wave merge into main when settle refuses, the conflict resolution, the sweep of leftover trees, the gate-lock capacity (`policy set`, T-0484 handoff), and release cutting (no plugin script mentions a tag or a release cut: grep `cut|tag` over `skills/*/SKILL.md` is empty; `.worktrees/release-0.20.{4,6,7}.NOTES.md` and the `release-0.22.2` branch merge `74e83d08` are the trace). Roles that skip a worktree: a solo in the primary checkout, which `solo_run.py` puts in a worktree only when another solo is already live there (`scripts/solo_run.py:33-35`, T-0345); chain roles, which edit the handoff's tree unless `dispatch.py prepare --tree <lane>` names one (`scripts/dispatch.py:654-655`), and the builder, which "edits code in the current tree" (`agents/builder.md:3`), its throwaway worktrees being base-check copies only (`builder.md:20`, `:23`). Fanout lanes, host sub-agent lanes (`isolation: worktree`) and `roll`'s scratch tree already have one.

(2) What a merge queue adds beyond the integration branch plus the gate lock, measured against what this repo paid for. Ordering: exists inside a wave (flock order plus `wait_for_overlap`) and does not exist across waves: waves 40 to 44 were open at once, each forked from a different main, and the step onto main had no order and no mechanism once main had moved. Auto-rebase: does not exist; `merge conflict` is a message to the sub-agent, and the integration-to-main step has no forward merge at all, which is why `settle` refused and the maintainer merged by hand. Retry: exists for the lock timeout only (T-0456). A bisect-friendly record of what each gate covered: `land.jsonl` is per lanes dir and gitignored; the committed ledger is T-0480's `gate-ledger.jsonl` (T-0481). So the queue's new parts are two: a forward merge with mechanical conflict resolution at the step onto main, and cross-wave ordering of that step. The evidence that these are the parts that cost: of the 8 first-parent wave merges into main since wave 38, 5 carry conflict-resolved paths (`git show --name-only` on a merge commit lists only paths resolved by hand): `.sdlc/AGENTS.md` four times, `.sdlc/roadmap.md` four times, `.sdlc/notes.md` once, `plugins/sdlc-lite/AGENTS.md` twice, `scripts/check.sh` once, `docs/references/sdlc-internals.md` once; two merge bodies keep the `# Conflicts:` list (`18f10dab`, `35f9a9b3`). The cause is not a builder outside a worktree: on the main side of each conflicting merge the commits that touched the generated files are the maintainer's own `File T-…`, `Close T-…` and `Triage` commits (20 of 23 main-side commits before wave 40's merge, 11 of 13 before wave 41, 2 of 2 before wave 42), each regenerating `roadmap.md` and the `.sdlc/AGENTS.md` block through `tickets.py new` or `close`, while the integration side's `close T-…` commits regenerated the same two files from a different ticket set (2 of 6 integration commits in wave 41, 10 of 30 in wave 42, 1 of 3 in wave 43). Two generators of one derived file on two branches always conflict textually and never conflict semantically: the right resolution is regeneration after the merge, which `tickets.py roadmap` does (`scripts/tickets.py:4`, `:99`, `:143`). `notes.md` is append-only (`tickets.py:20`) and takes a union merge. The three hand-edited files are real conflicts and stay with a person.

(3) Costs. Worktrees: 11 registered now, 87 directories under `.worktrees/` (most are retired lanes dirs whose `logs/` are kept by design), and `lanes.py list --stale` reports 7 closable lanes left behind: the integration trees of waves 40, 42 and 43, and the wave 44 lanes `i`, `k`, `l`, `m`. All three integration trees are closable today because main contains their branch after the hand merge, so a `settle` after the merge would have closed them; the duty at fanout `SKILL.md:51` and `conductor.md:9` has no script that notices when it was skipped. Rebase conflicts on generated files: 5 of 8 wave merges, as above; `check.sh`'s header comment and `plugins/sdlc-lite/AGENTS.md` are the hand-edited residue. Gate waits: three `gate waited 1800 s for a slot, not run` lines in `.worktrees/fanout42/logs/fanout.log` (lane b, T-0472, twice) and `.worktrees/fanout43/logs/fanout.log` (lane j, T-0385), each for a cheap gate (`claude_roles.py generate --check`, `check-packaging.py`); the holder is another repo's gates by the T-0484 handoff ("maison and sdlc-lite waiters queued 15 minutes after the capacity went from 6 to 20"), inferred, since `fanout.log` names no holder. `fanout.py` passes no `--priority` to `gate_lock.py` (grep `--priority` over `fanout.py`: no hit), so a land gate queues at priority 0 behind a builder's checks. A red gate blocking later merges: inside a wave a red resets its own merge (`:1483`) and the next land proceeds, so there is no head-of-line block today; with T-0481's `cover`, a red at the integration tip blocks only the fast-forward to main, which is the rule the handoff keeps, and the ledger's bisect line is the way out.

(4) Placement. A pipeline role needs a `levels.json` and `models.json` row (model and effort are the maintainer's, a non-goal here), an eval and `evals.py lock` (`check.py` fails without one), a `results.py` schema, `claude_roles.py` and `codex_roles.py` generation, and a `_role.sh` resolution for the hooks; and it would have nothing to reason about: every logistics step is a script call or a user approval. A second session agent beside `conductor` fails on one fact: publishing and the fast-forward to main need AskUserQuestion (`conductor.md:47`, fanout `SKILL.md:49`), which only the user-facing session can ask, and a sub-agent is denied `gh` and `git push` by `block-publish.sh`. So merge-ops is a conductor duty: a `## Merge ops` block in `agents/conductor.md` of about eight lines, the fanout skill's steps 4 and 5 rewritten to call the scripts below, and the recipe (background land with the journal as receipt, reading `lanes.py list --stale`) in `skills/handoff-format/run-operations.md`, the file every role reaches through `${CLAUDE_PLUGIN_ROOT}`. No new role, no 39th skill. The new terms join `check.py`'s agreement sets (`scripts/check.py:10`, `:30-37`) so the conductor, the fanout skill and `run-operations.md` cannot drift.

The duty block, in substance: enqueue is `fanout.py land <branch>` for every finished branch, as a background Bash call in an interactive session (`hooks/block-background.sh:9-10` exits 0 with no `SDLC_ROLE` and no `SDLC_HEADLESS`), so the session keeps dispatching while the merge lock orders the lands and the gates run; a `merge conflict` goes back to the sub-agent by name once. Dequeue onto main is, after the user picks it, `fanout.py settle <integration> --forward` (below) and then `lanes.py sweep --apply`; `lane still open` or an exit 2 comes to the user with the path, never a hand `git merge`. Queue status is `board.py --lanes` plus `lanes.py list --stale`; a `closable` row is a missed settle or sweep. A land gate runs at `--priority 1` (the policy `conductor.md:58` already states). Release cutting stays the maintainer's: version, notes and tag through AskUserQuestion, never from a role. Never: push, tag, publish, delete an unmerged branch, or move main by anything but a fast-forward.

(5) Boundaries, all already in force and kept: publishing only with the user's approval (`conductor.md:47`, `block-publish.sh`); main moves only by `--ff-only` (`settle`, `:2344`; `roll`, docstring `:82`; fanout `SKILL.md:49`); the forward merge lands on the integration branch, not main, and the fast-forward follows a full gate at the new tip, so the full-gate-before-ff rule is untouched; nothing deletes unmerged work (the landed test in `lanes.py`, the archive ref before any removal, `AGENTS.md` Lanes rules).

(6) Overlap and ordering with T-0480 and T-0481. T-0481 builds the per-merge gate class, `cover` (the full set at the integration tip, one ledger entry) and `settle --require-covered`. This design does not add a second ledger, gate class or cadence; it adds the forward merge in front of `cover` and the ordering of settles. Build order: T-0481 first (its handoff says one writer on `fanout.py` at a time), then the first build below, which calls `cover` as its gate; if T-0481 is dropped, the first build takes `--gate CMD...` on settle and runs the same gate loop in the integration tree instead.

Recommendation in one line: yes to a merge queue, realized as the existing integration branch plus a forward-merging, regenerating, serialized `settle`; no to a worktree for every builder as a blanket rule (the conflicts came from the maintainer's filing commits on main, not from builds in the checkout); merge-ops is a conductor duty block backed by scripts, not a role or a session agent. Pillar effect: performance and cost up (no hand merge per wave, no foreground wait on gates, no trees left to a later sweep); resilience unchanged, since main still moves only by a gated fast-forward and every refusal leaves both branches whole.

Stays project-side: the gate commands, `lane_setup`, `lane_sweep`, `lane_min_age_hours`, `hash_bound` and `light_scope` globs and the cover cadence (T-0480), the gate-lock capacity policy, watcher exclusions for `.worktrees/`, the release procedure, and any `.gitattributes` a repo wants for union merges of its own append-only files.

Smallest first build, one ticket, size L3, depends on T-0481: "fanout.py settle --forward: merge main into a diverged integration branch under the locks, regenerate the roadmap and the router block, union-merge notes.md, cover, then fast-forward". Red check, a `fanout.py selftest` case after case 28: a repo with two tickets; a lane lands T-0001 (its `close` regenerates `roadmap.md` and `.sdlc/AGENTS.md` on the integration branch); on main, `tickets.py new` files T-0003 (regenerating both files there); `settle fanout/x --forward --gate true`. Today: `fanout: fanout/x is not a fast-forward of main` on stderr, exit 2. Wanted: exit 0, `settled`, main's tip equal to the integration tip, `roadmap.md` on main listing T-0001 done and T-0003 proposed, `tickets.py check` exit 0, one ledger entry whose `to` is that tip. Negative controls in the same case: `README.md` edited on both sides exits 2 naming `README.md`, with main, the branch and the tree unchanged (`git status --porcelain` empty, no `MERGE_HEAD`); a plain `settle` without `--forward` on the diverged branch still exits 2; a red `--gate false` after the forward merge leaves main unmoved and the forward-merge commit on the integration branch. Later builds, not first: B (L2) `solo_run.py` defaults to `--worktree` when `lanes.list` shows an open integration lane in the repo, red check in `solo_run.py selftest`; C (L1) `gate_argv` passes `--priority 1` for a land gate, plus `gate_lock.py status` `ahead` and `blocking` (maison finding 7); T-0482 for the board view; T-0484 is filed.

### Rejected alternatives

- A new `merge-ops` pipeline role: a levels row and eval the handoff forbids deciding, generation on both hosts, and no reasoning task; every step is a script or an approval.
- A `merge-ops` session agent beside `conductor`: cannot ask the user, which the fast-forward, the push and the tag require; `block-publish.sh` denies it anyway.
- A new `merge-ops` skill: the fanout skill already holds steps 4 and 5; a 39th skill splits one procedure over two files and adds a routing target.
- A worktree for every builder as a blanket rule: the observed conflicts came from filing commits on main, not from builds in the checkout; the rule adds trees to a pile that already holds 7 closable lanes without a measured saving. Build B keeps the narrow rule (a worktree when a queue is open).
- Gates outside the merge lock (a scratch tree per candidate, as `roll` does): would let lands overlap, but needs a per-candidate tree and a re-merge on every gate pass; this repo's gates are cheap (T-0456) and the background land already keeps the session moving. Revisit with maison's 75 to 90 minute gates under T-0480's light class.
- A plugin-owned queue daemon or supervisor: the merge lock plus background lands already order the enqueue; a daemon adds a process to recover (resilience pillar) for ordering the evidence does not show missing.
- A `.gitattributes` merge driver for the generated files: project-side to install, silent on a bad regeneration, and `tickets.py roadmap` after the merge gives the same result inside the script where it can be checked and journaled.
- Resolving every conflict mechanically with `-X ours` or `-X theirs`: loses one side of a hand-edited file; the resolvable set is the three derived files and nothing else.
- Regenerating on main instead of the integration branch: puts a commit on main that no gate covered; the forward merge keeps main ff-only.

### Risks

- The regenerate-after-merge rule is only as good as `tickets.py roadmap` on the merged ticket set: a ticket folder renamed to `.NNNN-` on one side and edited on the other is a real conflict the regeneration cannot see; the refusal path must name it rather than regenerate over it. The selftest needs that control.
- `notes.md` union merge can duplicate a paragraph when both sides appended the same close note (a ticket closed twice); harmless but noisy; the journal line names the regenerated paths so it can be seen.
- Two settles racing on `settle.lock` are serialized, but the second re-merges main that now holds the first wave; a gate that was green at its own tip can be red at the combined tip, and the only answer is the ledger's bisect line (T-0481). Without T-0481 the first build must carry its own `--gate` loop or it ships an ungated fast-forward.
- Background lands in an interactive session depend on the completion notice; a session that ends before a land finishes leaves a half-done land (the flock is released by the OS, the journal line is missing). `land` already resets the merge on every failure path; the recipe must say to check `lanes.py list --stale` on resume.
- `--priority 1` for land gates across every repo on the machine changes nothing between repos and only beats builder checks; the real cause of the 1800 s waits is T-0484 and capacity, which this design does not fix.
- The duty block is prose; what makes it bite is `settle --forward` refusing less often and `lanes.py list --stale` being read, so build A without the fanout skill and `run-operations.md` edits would leave the hand merge as the easier path.
