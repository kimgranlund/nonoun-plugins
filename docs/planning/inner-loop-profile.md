# Inner-loop profile

Design from the T-0501 architect pass (2026-10-12), requested by the agent-ui factory. Not built. Opt-in through one `profile: inner-loop` line in `.sdlc/config`; no new role, no new verdict value; the suite moves from ticket criteria to the merge gate; one verifier per L2 and L3 ticket stays.

<!-- role=architect level=L1 model=fable effort=high -->
### Approach

Recommendation in one line: yes, ship the inner-loop profile as one opt-in line in `.sdlc/config` (`profile: inner-loop`) whose parts are config keys and prompt rules on top of scripts that already exist; no new role, no new verdict value, and the full suite moves from the ticket's criteria to the merge gate, which is the only place the plugin runs it today for a fanout lane. The profile changes what a ticket's checks name and where L3 tickets run; it changes nothing about independent verification: one verifier per ticket stays (solo.md `## Verification`, levels L2 and L3), the family rule stays (`dispatch.py prepare`), and the T-0496 skip stays separately gated by `tests_gate: pilot`.

Where the cost comes from, read from the records. Every agent-ui Done-when in the cited tickets names the full suite: T-0075 `.sdlc/shopkeeper-preset/handoff.md:20` ("npm run check and npm test exit 0"), T-0077 `.sdlc/basic-teaching-module/handoff.md:19`, T-0079 `.sdlc/bookingform-field-kinds/handoff.md:19` (all under `/Users/kimgranlund/Projects/nonoun/agent-ui`). So the suite runs once in the solo's checks (solo.md Loop 3 runs every check command and Run-verbatim runs each Done-when span), once in the verifier (verifier.md rule 1 runs each criterion; T-0075's `verifier-L2.md` #2 ran `npm test`, 14959 tests), a third time when the verifier applies rule 4 at the base in a throwaway worktree on a red gate, and a fourth at the merge. The ui-board-grid builder (`.sdlc/ui-board-grid/step-1.superseded-1/builder-L3.md`) ran `npm test` with 14845 tests and hit one timing assertion that passed alone: at load 36 to 40 (the retro's uptime line) the full suite is also the flaky one. The handoff's "10 to 20 extra minutes" is the factory's figure and is not in a record here [U]; the two to three runs per ticket are [V] from the files above.

(1) Local gate setting. Two repeatable lines in `.sdlc/config`, parsed by `tickets.py` beside `hash_bound:` (`plugins/sdlc/scripts/tickets.py:272-276` is the regex family; `hash_bound_globs` at `:453` is the reader shape): `local_gate: <cmd>` (the checks a solo, builder and verifier run: the repo check script plus the file-scoped tests the ticket names) and `full_gate: <cmd>` (the suite only the merge runs). The plugin cannot tell from text that `npm test` is a whole suite, so the owner declares it; the match is the exact span text. Consumers: `solo_run.py run` (`plugins/sdlc/scripts/solo_run.py:111-120` already reads the handoff and calls `steps.ticket_verifier`) refuses, exit 2, a handoff whose `## Acceptance criteria` or `Done when:` span (`results.criterion_spans`, `results.py:262`) equals a `full_gate:` command, printing the `local_gate:` lines to use instead, when the profile is on; it also appends `Checks: <local_gate lines>` to the brief when the brief names none, so the factory's one short brief needs no check list. `steps.py lint <planner.md>` adds the same refusal for a `(guard)` on a chain plan, which is planner rule 14's "named integration gate that runs after the lane" made mechanical. The verifier needs no change: it runs the criteria, and the criteria no longer hold the suite. The merge keeps it: `fanout.py land --gate "<full_gate>"` and `settle --forward --gate` (`fanout.py:2418-2447`), or the project's own merge script. Pillar: performance and cost (two to three suite runs per ticket removed, the flaky full-suite red moves to the one place that has a retry and a lock, `gate_lock.py`); quality unchanged because the suite still stands before main. Cost to build: L2, `tickets.py`, `solo_run.py`, `steps.py`.

(2) Pass with notes. Not a verdict value. `results.key_value` fullmatches the allowed regex (`results.py:42`), and twelve `== 'pass'` readers in `steps.py`, `fanout.py`, `dispatch.py`, `tickets.py`, `run_lifecycle.py` and `order.py` plus `run.sh:21` would each need the new value; `results.py` already ignores undeclared `## ` headings (`:15`), so a `## Notes` section costs nothing to parse. The rule, in `verifier.md` as one affirmative line: a finding that no criterion names (an em dash in a comment, a stale count or version comment, a comment nit) goes under `## Notes`, one line each with file:line, never into a criterion's state and never into the Verdict; the Verdict is `fail` only for a criterion that is red or a defect rule 2 names (a broken dependent). `results.py` adds `Notes` as an optional section of the verifier schema so `validate` keeps it in order. The closer carries the notes into the ticket: the factory's `tickets.py close --reason` text, or `fanout.py land`'s close reason (`fanout.py:941` composes it), so `tickets.py close` keeps reading no verifier result (the T-0400 invariant) and nothing is rebuilt or lost. The evidence has a limit the design must state: of the three cited reports only T-0075's exists in the main checkout (T-0077 and T-0079 folders hold no verifier result; they ran in lane worktrees [U]), and in T-0075 the nit was a Done-when clause, "records repaired in the same change" (`handoff.md:20`), so the verifier failed it by contract. The profile therefore also fixes the authoring side: under the profile a nit the repo cares about is a `local_gate:` command (agent-ui already greps em dashes: its `claude-md-em-dash` and `skills-em-dash-*` tickets), so the solo catches it before the verifier, and a nit no gate names is a note, never a Done-when. Boundary with T-0496: T-0496 decides whether a verifier runs at all (the `tests-gate` skip in `verify_scope.py`, gated by `tests_gate: pilot`); this part decides what a verifier that does run may fail. No overlap: a profile repo may set both. Pillar: performance (no rebuild round for a note; the retro counted about 15 minutes per ticket on three tickets), quality unchanged because every criterion still decides the verdict. Cost: L1, `verifier.md` plus `results.py` sections plus one `check.py` or `prompt_lint.py` case; the `verifier.md` prohibition count must not rise.

(4) Stalled agents. `dispatch.py status` already prints `last activity <age>` and `silent` at 30 minutes (`dispatch.py:556`, `:580-586`). The gap is `resume`: it refuses any attempt that is not `orphaned` or `interrupted` (`dispatch.py:610-611`), and a silent attempt is `running`. Recommendation: no relaunch at a lower level. The retro's cause was host load 36 to 40 and full-suite gates, which a lower level does not shorten; model and effort are user decisions (root `AGENTS.md`, Shared invariants); and a relaunch re-does the work with less capability on the ticket least able to afford it. The factory picks the rung. Pillar: resilience; cost L1 in `dispatch.py`.

(5) Merge path. The plugin's single documented path is `fanout.py settle <integration> --forward --gate "<cmd>"...` (T-0489, in 0.22.5: `fanout.py:2418-2447`, `settle_forward` at `:2473`; factory `## Merge ops` at `factory.md:50-54`; fanout `SKILL.md` section 5). It covers integration branch to local main by a gated fast-forward, and nothing else: the plugin has no PR model (grep `gh pr` over the scripts hits only `hooks/block-publish.sh:29`, which denies roles `gh pr create|merge|...`). agent-ui merges GitHub PRs (#1886 to #1889 in the retro), so its CI wait and squash guard are project side, in its `queue-merge.sh`, and the plugin states the contract that script must keep, two lines in `## Merge ops`: (a) the branch head contains the base tip before the merge (`git merge-base --is-ancestor origin/main HEAD`, by rebase or a merge commit; never a squash of a branch cut before the last merge, which is how #1888 reverted #1886 and #1887: a squash writes the PR's tree, not a merge), and (b) the gates ran at that head sha and none is pending (`gh pr checks <n> --watch --fail-fast` is the GitHub form; `gh pr checks` is read-only and not in the block-publish pattern). `settle --forward` already keeps both for the local path (merge main in, cover at the new tip, fast-forward). A plugin script that polls `gh` is rejected below. Pillar: resilience; cost L1, docs only (`factory.md`, fanout `SKILL.md`, `run-operations.md`).

(6) UI-parity criterion. A criterion line tagged `(parity)` (`leading_tags` at `steps.py:641` accepts `\(\w[\w-]*\)` tags): ``- (parity) `<capture command>` writes `<real.png>`; against `<mock.png>`: <property>, <property>, ...``. The handoff form: the mockup path and the capture command are the project's (agent-ui has `npm run test:browser` and Playwright); the criterion names at most five properties the verifier must see in both images (column count, gutter, a filled primary button, the heading order), never "matches". The verifier: runs the capture command as an observed run (verifier.md: runtime behavior passes only on an observed run), Reads both images, and records pass or fail per named property as the evidence; an unnamed difference is a note, under (2). There is no mechanical red for a visual judgment, which is why the properties are named: checks-that-bite applies to the capture command (it must fail when the page is missing), not to the eye. `steps.py lint` refuses a `(parity)` line that names fewer than two image paths or no property list. Level: `ticket_verifier` (`steps.py:3132-3159`) routes L3 only for size, merge, security, the `verifier: L3` line or a pinned label, so a styling ticket writes `verifier: L3` when the owner wants Fable's eyes; the default stays L2 and the pilot measures whether L2 misses parity. Pillar: quality (a styling approval becomes checkable); cost L2, `steps.py` lint, `skills/handoff-format/SKILL.md`, `verifier.md` one line.

(7) The profile. One line in `.sdlc/config`, `profile: inner-loop`, read by `tickets.py` (`profile(root)`, beside `merge_gate_declared`), and a per-ticket opt-out line `profile: default` in the handoff (the `merge_gate: full` precedent). Per repo, not per ticket, because its parts are repo facts (which command is the suite, which merge script runs). What it sets: lane, L1 and L2 unchanged (`steps.py` `LANE_SOLO_SIZES` already routes them solo, `:2962`); an L3 ticket with no merge step in its title and no security word goes to `solo-L3` with the one batched verifier instead of the chain, which is ceremony audit change 3 (chain L3 median $13.07 and 74 model minutes against solo L3 $10.91 and 49, n = 5 [U]) made a config choice; the planner and filer are what it cuts, and the audit found no catch of their own in the window. Checks: `local_gate:` lines are the brief's checks, `full_gate:` lines are refused in criteria and run at the merge (1). Verdict: `## Notes` (2), profile-independent. Merge: `settle --forward` or the project script under the two invariants (5). L4 and L5 are untouched (`steps.py lane` keeps `full`; `ticket_verifier` keeps L3), so verification risk at L3 and above is unchanged: one independent verifier still runs on every L2 and L3 ticket, and L4 and L5 keep the chain. Declaring it: `onboard.py` writes the line only when asked; this repo does not set it (its suite is `check.sh`, already a plan-time `(guard)` with a timeout).

Stays project side: the `local_gate:` and `full_gate:` commands; the em-dash and stale-count grep as a local gate; the PR merge script, the CI wait and the rebase policy; the screenshot capture command and the mockup files; the `verifier: L3` choice per styling ticket; the `tests_gate: pilot` decision (T-0496).

### Rejected alternatives

- A `pass with notes` Verdict value in `results.py`: twelve readers plus `run.sh` fullmatch `pass`; a `## Notes` section lists the same findings with no reader change.
- `tickets.py close` reading the verifier's notes itself: it reads no verifier result by the T-0400 design, and the closer already composes the reason text.
- Inferring the full suite from the span text (`npm test`, `check.sh`): the plugin cannot know a repo's suite; a declared `full_gate:` line is exact and cannot misfire.
- Relaunching a silent attempt at a lower level from `prepare`: silence came from host load and gate waits, not model capacity; model and effort are user decisions; the same-level ladder from `resume` keeps the choice with the factory.
- A plugin script that polls `gh pr checks` until no check is pending: the plugin has no PR model and roles are denied the merge anyway; two invariants in the Merge ops contract cover every project script.
- A per-ticket profile line as the primary switch: the suite command and the merge script are repo facts; the ticket keeps only the opt-out.
- A pixel-diff parity check in the plugin: the capture tool and the threshold are the project's; the plugin ships the criterion form and the verifier's duty.
- A new `inner-loop` role or lane value: `steps.py lane` already has solo for L1 and L2 and solo-L3 exists; the profile only moves L3 tickets without a merge step onto it.
- Making the em-dash and stale-count scan a plugin lint: a repo convention; it belongs in that repo's `local_gate:`.

### Risks

- A repo declares `full_gate:` but its ticket writes the suite in a paraphrase (`npx vitest run` instead of `npm test`): the exact match misses it and the suite runs again; the first wave on agent-ui shows whether a normalized match is needed.
- Routing L3 to solo-L3 under the profile removes the planner's criteria probes (T-0498) for those tickets; the solo's Run-verbatim rule reports a criterion that cannot pass, but after the build, not before; K-005 on profile L3 tickets is the guard, and the opt-out line is the brake.
- Notes that are never acted on accumulate in close notes; if the pilot shows the same note three times, the repo adds the grep to `local_gate:`.
- The parity criterion rests on a model's reading of two images; a wrong pass is possible and no red control exists for the judgment. The named-property form and the `verifier: L3` line bound it; a repo that needs certainty keeps a pixel diff as a `local_gate:`.
- The T-0077 and T-0079 evidence could not be read; if their fails were criteria too, part (2)'s mechanical change is smaller than the handoff assumed and the authoring rule (nits become local gates, not Done-whens) carries the gain.
- `solo_run.py` refusing a handoff at start adds one more exit code the factory must handle; it prints the fix on one line to keep that cost at one command.
