# Candidate exposure and retention

## Candidate territory

Hydration also extracts `candidates` from recorded messages, context and returned text. Catalog entries are available options; other literal paths are mentions. These remain separate from source exposures. Skill-root aliases are resolved only when the same trace declares the mapping. The atlas includes dotted candidate branches and timeline path counts; selecting one shows its exact provenance. Later attempted/read/edited exposures change its visible state. No observed attempt is not proof of evaluation, rejection, irrelevance or non-use. Include explicitly evidenced alternatives in decision analysis; never invent rejected routes. `scripts/candidates.py --data OLD.json --out NEW.json` upgrades an existing report without reading any candidate files. Run connections.py afterward to link later references.

## Exposure versus retention

The reusable shell derives exposure from candidates and recorded operations: available catalog option, encountered path, requested retrieval, partial return, full return. Edits are independent and never imply reading. Node fill encodes returns; noodles continue to encode routing relationships. All options / Contents observed / Confirmed inclusion filters operate at the replay cursor. Confirmed inclusion means a historical explicit inclusion record exists by that step, not persistent residency. Retention is confirmed/removed only at the corresponding assembly event; later retention is unknown, and compaction explicitly makes it unknown. Rules for explicit `contextRecords`: the Context records section of [the hydration contract](hydration.md).
