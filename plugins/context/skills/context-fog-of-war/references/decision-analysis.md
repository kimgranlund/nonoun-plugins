# Decision analysis / v2 hydration

The app answers questions such as “How did the harness know to use the custom menu?” Use the schema in `session.schema.json`. The v2 schema adds required `decisions`, `guidanceEdges`, and `findings` arrays; v1 reports remain loadable with an explicit no-analysis state.

## Build an answer from evidence

Locate the implementation choice or outcome first, then inspect preceding instructions, tool requests, and returned excerpts. A source path in a skill catalog means discovery, not a file read. Identify the earliest evidence of the choice, candidate guidance, intermediate route, and resulting action. Distinguish what the agent explicitly said it followed from what you infer.

A `decision` contains an ID, the user's question, a bounded answer, ordered `edgeIds`, and `evidence`. A `guidanceEdge` contains an ID, earlier `from` event and later `to` event, `kind`, `explanation`, and `evidence`:

- `explicit`: a recorded instruction or reference actually directs the transition. Quote it; do not infer compliance merely from its existence.
- `observed`: the trace establishes the sequence or call/result relationship, without causal attribution.
- `inferred`: a plausible influence supported by excerpts, explicitly qualified. State what remains unknown.

A citation is `{ "eventId": "e12", "excerpt": "exact substring from that event's evidence.text" }`. Python and browser validation reject dangling IDs and excerpts not present in the cited event. Pick the smallest relevant excerpt, not the whole payload. When evidence.text contains JSON escaping, preserve that exact representation. A matching substring establishes provenance, not correctness of the interpretation; review the surrounding evidence before drawing a conclusion.

## Diagnose routing

Create findings only for evidenced problems or actionable gaps. Unused context and exploration are not automatically waste. Distinguish a necessary alternative check from a misleading route, failed lookup, missing dependency, unsupported adapter, or overly restrictive instruction.

Each `finding` references a `decisionId` and contains:

- `title`, `category`: routing, lookup, dependency, coverage, or guidance.
- `observation`: what visibly happened.
- `hypothesis`: qualified explanation, with uncertainty when the link is not recorded.
- `target`: exact file, catalog entry, or routing rule to improve. A text target is not an instruction to edit it automatically.
- `improvement`: concrete proposed guidance or behavior.
- `verification`: a repeatable scenario and observable expected result, including correct negative routing where appropriate.
- `status`: `proposed`, `applied-unverified`, or `verified-in-session`. The last status requires evidence of the verification, and claims should stay within that test's scope.
- `evidence`: exact cited excerpts supporting the finding.

A report diagnoses and recommends; it does not apply recommendations unless the user asks for those edits. To turn findings into fixes on a runtime harness that renders generative UI, classify each failing cluster and choose its fix layer with the [runtime-harness learnings](learnings/README.md). When a fix already occurred in the session, identify it and cite the verification rather than presenting it as a new proposal. Do not claim downstream user success from a local unit test.

## Presentation boundaries

Decision analysis is retrospective and independent of the replay slider. Evidence buttons jump to the corresponding replay event. The timeline/map remain exposure history, not a representation of hidden reasoning. If the trace cannot establish why a choice occurred, say so and show the missing link. When no finding is supported, leave findings empty for that decision rather than inventing an optimization.

For source-specific routing, add optional `sourceIds` to a guidance edge, referencing the exact sources supported by its quoted evidence. Do not assign every source from a compound read: disambiguate its returned excerpt and explain the link. The atlas draws source-to-destination trails only for these explicit attributions, preserving explicit/observed/inferred kinds. Omitted attribution means unknown, not unused.

Automatic links are generated by `scripts/connections.py` during hydration. Existing reports can be upgraded with `python3 scripts/connections.py --data OLD.json --out NEW.json`. Auto IDs use the reserved `auto-source-` prefix and are replaced idempotently; reviewed edges are preserved. Exact path reuse is observed, not causal. Literal guidance reuse requires an attributable single-source read and is inferred. During the skill run, also review consequential semantic transitions without asking the user to annotate them; quote the returned guidance and the downstream action, name supported sourceIds, and qualify inference. Unresolved compound-output attribution remains an explicit gap. Never promote lexical similarity to explicit causation.
