GENERATIVE SYSTEMS / DEVELOPER REFERENCE

Context → execution → evidence → improvement

A context-based harness delivers authoritative materials to an author, assembles the submitted source through trusted mechanics, and observes real outcomes. Control comes from explicit ownership, versioned boundaries and qualified checks. The diagrams describe the skill’s workflow, not a shipped universal harness.

Full lifecycle

Read the top row left to right, then the lower row right to left. Solid arrows carry the current artifact through delivery; dashed arrows represent controlled feedback.

Inner loop: author repair

In ordinary authoring, self-check and repair the editable source. Reuse unaffected evidence. A runtime-owned fault requires a change to its owner, rather than a local workaround that replaces trusted mechanics.

Outer loop: corpus improvement

Classify observed drift, update the responsible owner, and publish derived views only through the authorized workflow. A documentation change becomes an efficacy claim only after an appropriate independent comparison.

Delivery boundary

Checks inform review. They do not create authorization to publish, expand scope or erase accepted limitations. Record exactly which version and environment were assessed.

Nested evaluation loops

The harness must be qualified before consuming author attempts. Experiments may restrict repair at first submission; this restriction does not govern ordinary authoring.

Loop A: qualify the oracle

A legitimate artifact must pass. A deliberately missing association, hidden error or stale invalid state must fail for the expected reason. Verify the mutation reached the exercised source.

Loop B: diagnose and reanalyze

If the evaluator was wrong, keep the original verdict and reanalyze all affected conditions equally. This is evaluator correction, not improved generation.

Loop C: improve and confirm

Change one coherent boundary, freeze a new cohort and confirm on a fresh brief. Preserve sealed holdouts. Count timeouts and incomplete submissions; viewports are checks, not independent author samples.

Practical controls

Before execution

Resolve authoritative owners; declare editable/generated/immutable files; freeze acceptance, repair policy, attempt and time budgets. Check for an equivalent completed batch.

During execution

Keep evaluator telemetry outside author context. Preserve first submissions and original revisions. Directory isolation on an unrestricted same-user filesystem is not a security boundary.

After execution

Separate structural, runtime, behavioral and visual verdicts. Record source identity and environment. Run affected checks, retain failures and publish only authorized current materials.

Example: conditional validation and context budget

For a region/channel restriction, derive every affected control or supported semantic group from the contract. Check visible error association at rejection and cleared invalid state at recovery. Persistent helper descriptions may remain. An alert alone does not establish association.

For authoring, read the contract, source and declarations once; retrieve a duplicate recipe only for a missing seam or adaptation. Smaller planned read bytes are a budget observation. Measure behavior and actual retrieval overhead separately before claiming improvement.
