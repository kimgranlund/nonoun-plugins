# Generation and revision

Use when building a generation pipeline or revising an artifact. Separate trusted reusable mechanics from the authored surface, and make their join explicit.

## Choose the generation boundary

Choose the narrowest representation that expresses the authorized task without hiding required behavior. Constrained composition suits supported combinations with explicit limits; template seams suit stable mechanics with bounded edits; free generation suits authorized logic outside those boundaries. Weigh recurring failure evidence against the maintenance cost of schemas, compilers and adapters. A repair-rate plateau alone does not justify a compiler.

State whether a mechanism prevents an invalid choice, rejects an invalid submission, or merely reports it after execution. Structural constraints do not prove runtime behavior. If the representation cannot express the outcome, route the capability gap rather than silently escaping its boundary.

## Define the seam

State which files/fields are editable, which are generated, what the assembler expects and what owns identity. Preserve required host slots when customizing a template. Mark optional slots explicitly and tolerate their omission only where the implementation contract allows it. Byte-identical helper reuse is a useful boundary check, not proof that its host still integrates.

Keep source shape and placement separate. A standalone leaf may own page padding without changing its manifest kind into a composition. Inspect the actual source interface rather than deriving structure from a visual label. Where the system duplicates an editable value, document which copy wins; verify synchronization. One-source architecture can simplify maintenance, but a deterministic wrong-copy diagnostic does not demonstrate better fresh generation.

Use the supplied API and mounted scope for interactive code. Startup success does not prove that an action can reach a callback. Confirm how native activation becomes an event; a shell may suppress default submission, so a submit-only controller can remain inert. Do not replace the runtime to compensate for a missing declaration or unsupported event path.

State, validation, rendering and bindings need declared owners. Retain an established error while its rule remains violated after an edit; do not infer resolution from the edited field/group alone. Clear resolved rules independently, preserving other active errors and the last receipt. Pristine validation timing remains a domain decision. Capture edits into state and render from that state. Bind through the supported mounted lifecycle, with cleanup for resources outside it. Preserve values across the remounts the contract supports; do not promise persistence across reload if it is only session-local.

## Revise with provenance

Preserve the original authoring inputs and delivered output before making a successor. Follow the project's existing revision scheme; numbered folders are one option, not a universal rule. Trace which source, controller and authoritative materials produced each result. Check original-source preservation independently of successor behavior: a functioning revision can still overwrite its baseline.

Generate into a fresh staging destination. Retain failure receipts and diagnostics; distinguish unsuccessful staging from delivered output. Promote only the authorized result after applicable checks. Do not patch evaluator copies and count the repair as first-pass author success.

Reuse completed checks when artifact, criteria, relevant dependencies and tested environment still match. Follow existing source-to-consumer links: a changed validation helper affects its consumers' invalid-input and recovery claims, while unrelated typography evidence may remain current. Uncertain dependencies need assessment. A changed assertion needs qualified reanalysis of retained output, not a generation-improvement claim. Use the existing assessment owner; hash identity does not establish completeness or independence.

Deliver a clear source-to-output map, current build status and remaining limits. Use [verification and drift](verification-and-drift.md) for behavior and acceptance; ordinary authoring may self-check and repair. First-submission restrictions belong to specifically designed experiments, not future generation policy.
