# Materials and contracts

Use when defining or consuming authoritative kits, templates, assets and schemas. Identify what each material controls before copying it into context or output.

| Material | Authority |
| --- | --- |
| Raw declarations | Exact values and names |
| Semantic declarations | Roles, relationships, supported mappings |
| Capability contract | Intent, prerequisites, anatomy, states and limits |
| Schema or manifest | Interchange shape, identity and references |
| Recipe | A concrete supported adaptation |
| Executable implementation | Actual supplied mechanics |
| Evidence | What was observed under stated conditions |

These can disagree. Do not silently elevate an example or historical report above the current owner. Resolve conflicts against the applicable version; verify implementation where the contract's claim matters.

## Contract content

An early capability may contain only identity, intent, boundaries and unknowns; extend it as facts become available rather than inventing requirements. Progressive Context owns durable capability records and reuse assessments when present; use existing records without adding a dependency on that skill.

For a reusable capability, capture intent, when to use it, required structure, optional slots, dependencies, editable seams, supported states, failure behavior and verification boundary. For executable APIs add exact names and signatures, module/lexical/global scope, callback arguments, initialization and activation timing, ownership, cleanup and return behavior. A helper in a catalogue is not automatically part of the supplied runtime.

Before advertising supplied mechanics or a template beyond its original integration, exercise the declared interface from a separate consumer and report undeclared context or dependencies. Original-host success and byte parity do not establish that boundary. Bind the result to source/dependency identities and the tested use in the project's existing assessment; Progressive Context owns that durable reuse qualification. One-off delivery needs no portability study, and separate consumption implies no evaluator isolation.

A recipe should demonstrate a real adaptation gap. A single-value radio example may not teach collecting multiple checkboxes. Collection access should use its declared mounted/group owner; an optional missing owner must not silently become an empty valid result. Avoid adding a broad example library when one bounded recipe resolves the observed ambiguity.

Schemas should locate optional fields in their containing object, not just describe an isolated entry. References must resolve actual targets. For example, a declared interaction target must identify the element using the system's identity mechanism; a similarly named event-selector attribute may not count.

A behavior-only fixture with a simplified kit does not establish fidelity to another design system. For dogfooding, deliver the actual authoritative assets and anatomy contracts, record their identity, and inspect computed roles as well as interactions. Keep the fixture runtime boundary explicit.

## Resolve a capability gap

Record the originating task and source version, unmet scenario, gap category, owner, disposition and permitted interim behavior using the project's existing tracking mechanism. Distinguish missing capability, failed discovery, contract conflict, runtime defect, evaluator defect and unclear intent. A supported fallback may proceed if it still meets the outcome; an extension must fit the authorized scope. Otherwise mark the affected work blocked while continuing independent work.

Resolve the gap in its owning source, verify the originating scenario and state how the original task resumes. Rejection needs a reason and an explicit fallback, scope decision or continued blocked status. Give temporary exceptions a scope and retirement condition. Closing the record does not establish that the original artifact passes.

## Consume without inventing fidelity

Inspect supplied assets and their provenance. Use declared tokens and icon names, with their actual fill/stroke and inherited styling behavior. Successful imports do not prove visible rendering. Missing context, manifest or assets remain labelled gaps; generated reference pages must not invent them to look complete.

Derived documentation should expose the declaration/source it renders and distinguish raw values from resolved semantic values. Keep a single authoritative owner for each fact; link to it rather than editing generated copies independently. If a transformation changes precision or representation, preserve the original declaration and identify the conversion.

Non-UI example: a document template may own section styles and merge-field names, while an editorial brief owns the content. A heading's visual appearance does not authorize renaming a merge field. A valid document container does not prove all required sections were populated. Apply the relevant domain tools and checks rather than substituting UI conventions.

The result is a material-to-authority map, applicable contracts and explicit gaps. For assembly and revision ownership read [generation and revision](generation-and-revision.md).
