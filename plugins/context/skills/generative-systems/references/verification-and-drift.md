# Verification and drift

Use to diagnose a fault or assess readiness. Derive criteria from the requested outcome and authoritative constraints before examining the result. Keep layers separate: generation, structural validity, startup, activation, task success and visual quality.

Before generation, connect the requested outcome to representative scenarios: starting conditions, action, observable result and relevant failure or recovery. Trace acceptance criteria to those scenarios or authoritative constraints. Surface assumptions and resolve contradictions that would change implementation. Require a particular structure only when the outcome or owning contract requires it. A legitimate alternative should pass; a plausible-looking result that misses the outcome should fail. Preserve intent ownership: changing criteria to fit generated output requires a justified scope decision and re-evaluation of affected evidence, not a silent relaxation.

## Find the failing boundary

Classify with evidence: unavailable/out-of-scope delivery; absent or partial retrieval; implementation inconsistent with observed guidance; application/submission error; runtime/assembly defect; evaluator defect; environment limitation. Use “consistent with” when traces cannot establish the mechanism. A failure in one package does not prove a format failure.

Inspect retained source and the actual failure message before generalizing. A single-leaf assembler can reject page kind even when ID is correct. A checkbox can immediately revert because a handler queries an absent form and dispatches an empty collection; later Save or remount failures may be downstream effects. Correct a mistaken diagnosis in a successor note without rewriting historical verdicts.

## Identify what enforces a constraint

Separate advisory instructions, post-action feedback, pre-action blocking and final acceptance. Name the actions and environments each mechanism covers and what happens when it is absent, fails or times out. Feedback after an operation cannot prove that operation was prevented. A completed author session is not an acceptance result.

For a claimed enforcement boundary, qualify an allowed case and a deliberate violation through each materially distinct covered path, including failure of the gate itself. Keep uncovered paths explicit. Where acceptance is required, bind its evidence to the final artifact and relevant dependencies. Bound automatic repair by task-appropriate attempts or time; exhausted repair retains an unaccepted result and a next owner rather than weakening criteria.

## Checks that discriminate

Pair a known-valid case with a fault that should fail for the relevant reason. Validate the checker itself before trusting a new gate. Reuse unchanged qualification only within its tested scope; changed assertions require the affected valid and fault controls to run again. Confirm injected faults reach the exercised artifact. Keep failures collected independently where possible: a failed edit must not hide whether keyboard activation works. Use fresh scenario setup to prevent prior state from making a later criterion pass accidentally.

Exercise actual user-triggered paths: pointer and focused-button keyboard activation, invalid values, changed values, repeated actions, recovery and supported remounts. Focus must be measured in the actual owner document. Distinguish committed transitions from typing or initial mount; heading focus appropriate for a transition may be harmful on every render.

Check visible outcomes. Hidden initialized reports are not success evidence. Allow supported output/status/live-region structures without requiring one decorative layout. Observe actual effective theme and rendered width, especially an opened popup/dialog; requested dimensions or zero width while closed are insufficient. Capture-only adjustments must remain separate from behavior evidence.

Static checks can reject malformed schema, missing targets or unknown tokens. They cannot prove interaction, accessible reading order or visual quality. Passing keyboard behavior does not certify screen readers. Visual measures require the real surface, font, inherited styles and relevant state.

## Error association and recovery

Derive affected controls or semantic groups from the domain contract before testing. Require feedback coverage for each of them, not merely any control with a referenced text node. Resolve aria-describedby/aria-errormessage targets in the owner document and check that the intended error is nonempty and visible in the invalid state. A live alert alone does not establish control association. Use declared group-level association where supported; do not impose a fixture's per-radio markup on every design.

Test an edit that leaves the violated predicate true, including another choice in the same group: established feedback and invalid flags must remain. Then test partial recovery before another Save; only resolved rules clear. Keep pristine validation timing separate from established-error retention. After valid recovery, verify invalid flags clear and obsolete errors disappear. Persistent helper descriptions may remain. Qualify the oracle with separate missing-association faults for each affected target, unrelated-only association, hidden error and stale invalid state. Confirm each mutation actually changed the exercised source before interpreting its verdict. DOM checks do not certify screen-reader announcements.

## Report and preserve

Record exact artifact/check identities, environment, setup, result and unexecuted coverage. Reanalyze retained bytes when a qualified evaluator correction is needed, keeping the original verdict and applying the correction to every affected condition. Reanalysis is not generation improvement.

Reuse unaffected evidence and run affected checks. An accepted limitation remains scoped to that delivery and is not a universal waiver. Report confidence within the tested boundary; neither declaration nor source parity establishes full-system reliability. For efficacy comparisons read [rapid experiments](rapid-experiments.md).

Check provenance must separate dependency resolution, timestamped launch history, author activation, independent evaluator behavior, untested conditions and delivery mode. Rejected discovery candidates do not negate a successful resolved module. Launch-only evidence cannot establish task acceptance. When available, base-ui verification-reporting supplies a bounded structured consistency check; provenance consistency still does not independently prove execution.
