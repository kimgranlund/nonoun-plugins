# Evidence, repairs and report template

## Interpret evidence

- Static pointer resolution proves reachability, not reading, understanding or successful implementation.
- Agent-reported paths are self-reported. Distinguish them from tool transcripts and independently inspected source/browser results.
- Record a failed guessed path and recovery, even when the task eventually passes. A broad truncated read is incomplete until missing governing sections are recovered.
- Compare current manifest/contract text with runtime/CSS/resolver behavior. An implementation that works despite omitted parent metadata reveals a documentation gap, not evidence that the unsupported composition is safe everywhere.
- Existing scripts may discover examples dynamically while stale documentation/log messages still report fixed counts. Check the actual inventory; avoid hardcoding counts into reusable guidance.
- Skills can contain older defaults. Follow current repository authority and report contradictions rather than importing old constants.
- Keep independent initial results separate from any supplied API locations, fixes or follow-up coaching. The latter can verify integration but cannot repair the original fresh score retroactively.

## Retrieval cost and route correctness

Record the minimum useful read trace: governing bodies reached, unnecessary guesses, repeated reads, clipped output and recovery, and relevant sections still unread. Use available tool evidence; label participant-only accounts as self-reported. Report measured calls, bytes, tokens or elapsed time only when actually available, and do not equate a long report with measured retrieval cost.

A route can succeed with avoidable overhead. Distinguish a wrong guess despite a returned canonical path from a missing or misleading route. Likewise, many bounded continuation reads can recover every required section without clipping; that establishes completeness, not efficiency. Do not reward fewer calls when they hide omitted authority, or require one tool call per document when small independent reads fit safely together.

Prefer task-scoped projections, exact returned paths and relevant sections, then follow their governing bodies and recover all required omissions. Reuse already-read unchanged authority within the trial. When overhead is demonstrated, repair redundant routing or ambiguous ownership in its existing repository owner; do not shorten participant briefs by supplying the answers, copy a handbook into this skill, or build a new reader merely to reduce call counts.

Record when authority was read, not just whether it eventually appeared in the trace. A guessed token or composition corrected during late source review is a self-correction; it does not establish that governing guidance informed the original implementation. Use returned command syntax and selective contract records where provided, while honoring the repository's delivery rules. Separate necessary continuation reads from avoidable full-inventory reads and rereads. A narrow task with a long trace is a reason to inspect relevance and duplication, not permission to skip required guidance.

## Lessons from real implementation trials

- A standalone example can build and render successfully yet be omitted by the root verification inventory. Ask the participant to locate both the authored example destination and how the root command discovers it; independently verify the new example actually participates. Do not copy a legacy example location just because its build wrapper is convenient.
- Discover verification commands from declared package scripts and their scope. A guessed per-component script may not exist; distinguish package tests, type checks, component browser suites and actual application visual checks.
- A duplicate-action test must assert the stable final outcome after competing work would have settled. Merely issuing duplicate actions and observing a transient error may miss a later success overwriting it.
- Inspect both the authored component demonstration and the consumer when they exercise different capabilities. A field-only demo may need focused field/control measurements when a shared geometry checker only covers containers; report that scope instead of counting an empty check as success.
- Fresh agents must be able to find verbal house-style rules (naming, CSS/token/recipe ownership and applicable states/variants/modes), not only scattered examples. Link authoritative rules from the normal author/consumer route rather than placing repository conventions in this review skill.

- Test shared setup through each actual delivery path. A routed app and a standalone example may need the same foundation entry, yet only one guide may name it. Inspect generated imports as well as the plan; a successful build can omit motion, typography or readiness defaults.
- Verify ownership after changes, not only at first render. A parent inspector or preview controller can silently reapply geometry over locally configured examples. Exercise a parent update after a local change and check which inputs survive according to the actual ownership contract. Keep any exemption in that integration owner; do not turn a specimen marker into a public component API.
- A declared font family is not evidence that its font asset loaded. Inspect the generated delivery for explicit assets, then check the required face actually loads before measuring text or accepting screenshots. Record fallback/offline behavior separately; a build or CSS token import can succeed while the browser uses a fallback font.
- Confirm participants discover the repository's common terms and actual metadata field names through normal routes. Do not put those answers in the neutral brief. Prefer a short dictionary and explicit owner links over new synonyms, copied manuals or a second registry.
- Separate a wrong guessed path from a broken route. Record the failed lookup and recovery; repair repeated ambiguity at the entry or owner, not by teaching every answer in the trial prompt.
- Extend existing state tests through ordinary cleanup events: a status may render correctly initially but disappear on blur, pointer leave or reconnect. Reproduce the failure before crediting a repair.

## Diagnosis and bounded repair

For each gap record: expected outcome → observed failure → source evidence → cause category → smallest correction → discriminating recheck. Do not assume every failed build is a context-routing defect. Distinguish unavailable tooling from broken guidance, and application code defects from missing contracts.

Use existing package scripts and returned documentation paths first. Shared source changes need coordinated ownership; generated bundles must be rebuilt from source. Preserve historical evidence, appending corrections rather than rewriting the previous run. Recheck links and affected behavior after a fix. A new clean agent is necessary only when claiming a discovery improvement, not for every small source correction.

## Final source and verification

Agree on a final source-ready handoff after the participant's own source review. Freeze the relevant files while integrated verification runs; record a revision or hashes where practical. Readiness coordination is an environment/ownership fact, so it may be included in neutral dispatches and follow-ups without revealing evaluator probes. Preliminary checks can inform work, but only checks against the delivered source support the final result.

If a source correction arrives after a check, identify the affected outputs and assertions, rebuild those outputs and rerun the relevant checks before claiming success. Preserve which results were preliminary; do not repeat unaffected suites without a reason. Distinguish source changes from report-only reconciliation. Finalize coverage evidence and hashes after the referenced reports/logs stop changing; a valid old hash does not prove a test covered new source. A freeze coordinates work, not a ban on fixing a confirmed defect.

For visual checks, wait for component readiness and the intended settled state before capturing. Use observable state or transition completion where possible. A mid-transition fill or disabled paint is not by itself a product defect. Likewise, a checker that finds no applicable hosts supplies no coverage; record its limit and use a focused check for the actual surface rather than widening the run merely to obtain a pass.

## Compact result template

- State: pending / in_progress / blocked / completed / cancelled.
- Scope, mode, starting revision/hashes, frozen acceptance reference.
- Participants: context isolation, entry, writable boundary, report location.
- Author: discovered route, decisions/artifacts, acceptance IDs and outcomes.
- Consumer: discovered route, decisions/artifacts, acceptance IDs and outcomes.
- Retrieval: route correctness separately from avoidable overhead; failed guesses, repeated reads, truncation/recovery and unread required sections; measured cost only if available.
- Evidence: final source revision/hashes, preliminary versus final checks, self-report versus independent source/build/browser checks, commands/results, screenshots where inspected.
- Repairs: cause category, authored paths, recheck; separate initial, assisted integration and fresh rerun outcomes.
- Limits/blockers: unavailable platforms, unrun criteria, remaining failures, next action.
- Shared notes destination and generated artifact ownership.

A useful negative control must distinguish a broken result from a working one: for example, a stale route should fail resolution, a busy click should not submit twice, or a missing screenshot should remain unverified. Do not add redundant tests that merely match the report's wording.


## Where to retain a lesson

Keep reusable review mechanics in this skill. Keep project vocabulary, manifest field names, foundation imports and API rules in the repository's existing owners. Update a broader UI skill only when its active instructions conflict with current project routing; distinguish frozen source snapshots from current guidance. Prefer updating one existing owner to creating another skill or copying the same rule across skills. Validate changed skill metadata/links separately from repository discovery trials; a clean repository trial does not by itself validate skill execution.
