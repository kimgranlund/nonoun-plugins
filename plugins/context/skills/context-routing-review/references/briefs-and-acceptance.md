# Reusable briefs and acceptance

The evaluator fills these fields before dispatch. Unresolved required environment facts are blockers, not permission to claim success. Share product requirements with participants; retain grading details, expected routes, known faults and previous answers with the evaluator.

## Trial envelope (evaluator)

- Repository entry and source revision/hash:
- Mode: static / fresh planning / end-to-end:
- Author task and Consumer task:
- Participant writable scopes and separate report destinations:
- Existing build/test/browser tooling, command scopes, automatic example discovery and output ownership:
- Final source-ready handoff, shared-build owner and handling of edits after verification starts:
- Required platforms/views and unavailable environments:
- Frozen acceptance IDs, observable pass conditions and evidence required:
- Known historical answer locations excluded from participant discovery:
- Bound: initial trial, affected fresh rerun if needed; further work only if justified/requested.

## Author brief (participant)

> Starting only at ENTRY, discover how this repository authors reusable capabilities. TASK: add/change CAPABILITY with PRODUCT_BEHAVIOR. MODE is MODE. You own EDIT_SCOPE; put your report in OUTPUT. Preserve unrelated changes and generated output ownership. Environment facts: ENVIRONMENT. Follow the entry's routes before acting; do not read prior evaluation answers or shared historical task logs. Record actual reads, failed lookups, recovered truncation, assumptions, source changes and checks. If required behavior belongs elsewhere, report the ownership boundary instead of patching unrelated files. In planning mode, deliver a concrete implementation/verification plan and make no source edits. Do not claim checks you did not run.

## Consumer brief (participant)

> Starting only at ENTRY, discover how to compose a SCREEN/WORKFLOW using existing supported APIs. PRODUCT_REQUIREMENTS. MODE is MODE. You own EDIT_SCOPE; report in OUTPUT. Environment facts: ENVIRONMENT. Discover current construction, geometry, registration/assets and verification rules through the entry. Record actual reads and recoveries. Exclude prior evaluation answers/shared historical logs. When a reusable capability is missing, identify its owning route and stop dependent work or use an explicitly accepted reduced scope; do not silently recreate it in application code. In planning mode, produce a concrete assembly and verification plan, without source edits.

Preserve the supplied product scope when extracting a brief. Do not add persistence, editable fields or new workflows merely to make a trial more demanding; propose such changes separately when task selection is open. Keep diagnostic checks learned from prior failures in evaluator criteria. For example, a specific parent-update sequence or font-loading probe belongs in the evaluator plan unless the user's product brief explicitly requires it. A neutral statement of the intended behavior is sufficient; do not turn the hidden check into a participant requirement.

Before dispatch, audit each participant sentence against the supplied product request, ownership boundary or necessary environment fact. Remove any sentence derived only from evaluator evidence or a known failure, even when paraphrased as desired behavior. For example, if the product asks only for independent appearance controls, do not add “retain local choices as surrounding settings change” from a parent-overwrite finding; keep that check evaluator-only. Save the audit separately from participant payloads.

Keep the separation through dispatch and follow-up, not only in the saved brief. Send the exact audited payload with only necessary environment/ownership coordination; audit any added message for hints too. Participants may independently discover geometry ownership, font requirements or other evaluated rules in governing repository docs. That is successful discovery, not a reason to remove those rules from the repo. After delivery, label transmitted evaluation results as evaluator-reported and repairs as integration work. Do not count participant-selected extras as requirements that the neutral brief imposed. Distinguish “not required” from “forbidden”: do not mandate an unrequested feature or prohibit a reasonable implementation choice without a scope constraint. If an optional choice materially expands the task, discuss that expansion explicitly.

Dispatch only the participant section, never this whole file or a combined brief/rubric report. The participant brief must not ask the participant to read this review skill, its references or evaluator examples. Domain skills discovered through the repository entry remain available. A skill-validation evaluator may receive this skill; label that run a skill-execution check. Keep evaluator acceptance externally frozen before candidate results; criteria authored during a review are prospective and cannot retroactively grade that review as a blinded trial.

## Adaptable acceptance matrix (evaluator)

| ID | Observable condition | Evidence |
|---|---|---|
| R1 | Governing author/consumer bodies reached before decisions; required omitted content recovered | Read trace with file/section and recoveries; source inspection |
| R2 | Current ownership, supported relationships and public APIs identified; missing capability escalated correctly | Cited authorities and implementation/plan comparison |
| R3 | Generated artifacts and historical evidence remain separate from editable authority; a new example is included by the declared verification inventory | Changed-file review, output locations and actual build discovery |
| A1 | Public API, behavior, styles, metadata/docs and meaningful tests agree | Source diff, registry result, focused checks |
| A2 | State changes preserve declared invariants and recover correctly, including local inputs after parent updates where applicable | Behavioral/browser evidence; in planning mode only proposed checks |
| C1 | Consumer uses supported composition, explicit assets/registration and independent layout decisions | Assembly map/import review/build; actual required font/asset loading |
| C2 | Validation, async success/error/retry and state preservation satisfy product brief | Actual interaction checks, snapshots, no duplicate action |
| V1 | Applicable desktop/narrow and light/dark states have no unintended overflow or visual regression | Inspected screenshots plus measurements |
| V2 | Claims match mode and measured environment; no invented AT/platform certification | Evidence report with unverified items |

When the reported failure concerns setup or vocabulary, freeze checks for discovery of common terms, actual metadata keys and the shared foundation used by the selected delivery path. Keep their names/paths in evaluator criteria, not participant briefs. Inspect the plan or authored imports rather than counting a mention as use.

Select only applicable rows and add task-specific assertions. Do not score missing browser evidence as a pass. Distinguish failed, blocked, not run and not applicable.
