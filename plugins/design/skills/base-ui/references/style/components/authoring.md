# Component authoring route

Read shared constraints once with `python3 scripts/run.py component-context.mjs --shared`. Request used records in small batches, e.g. `python3 scripts/run.py component-context.mjs --records choices,fields --record-only`; use additional batches or `ID --record-only` for later additions. Each batch rejects output above 12,000 bytes; split it rather than increasing the budget. Reuse returned records. Known IDs need no `--list`; use it only for discovery. Dedicated native-select/navigation-menu lookups return their own complete contracts. Reuse returned records in the session; reread only when the relevant source changes. Do not read the entire family README, catalog runtime or contract merely to find anatomy. For a new page, retrieve the recipe named by the used record and assemble it with `python3 scripts/run.py build-page.mjs FRAGMENT NEW_DIRECTORY [CONTROLLER]`. Use scripts/build.mjs only for an explicitly single-file export. The optional wireframe-review host offers demonstration-context.mjs for its own review demonstrations; that host is not a prerequisite here.

For local behavior retrieve `component-context.mjs --runtime`; create one UI runtime and mount definitions with explicit root/stateKey. Keep DOM access inside mounted render/bind. Review registration belongs to wireframe-review. For a required-title staged flow use the stepper transitionContract and its title-request recipe. For submitted native choices use choices.authoringExample; its inner editor preserves host margin.

Before markup, map each used family to its exact anatomy and native/JavaScript owner. Layout classes do not style native marks: checkbox uses `input.checkbox__control`, radio uses `input.radio__control`, inside the contract's associated label/body composition. Switch follows its separate contract. Do not replace the input semantics. Choice groups use field-group__root plus an inner options__root; choose plain inside cards. Workspace-specific options follow choices.nestedOptions, inside one choice container as sibling labels, never inside its radio label. Staged flows require the [focus and task guide](workflow-patterns.md#focus-and-task-grouping), including the runtime-supplied helper and actual Next/Back checks; use the stepper contract and maintained example: use form.stepper__root and ol.stepper__indicator[data-step-layout=adaptive][role=list] with the explicit indicator/title/status/check slots. Minimal native numbering is an explicitly requested fallback, not the generation default. Identify the current li with aria-current="step" and expose current/completed/upcoming text labels. Upcoming does not mean unavailable; unavailable/branching stages require a separate declared implementation.

Before adding a token reference, look up its exact name with `generate-token-index.mjs --group NAME` (color, typography, geometry, layout or profile). Groups return at most80 names with total/nextOffset; request --offset NEXT only if needed. Null nextOffset means complete; never treat a page as the whole group. Reuse returned names; never guess a name or hide a miss behind a fallback. The generator rejects unknown references.

For exclusive collection filters, use the navigation record’s filterAnatomy: direct aria-pressed buttons in segments__root. Options use Hc=2n+d, gap d/4 and container margin d/2. data-compact removes only the container margin. For moving selected/hover backgrounds, bind assets/recipes/segment-indicators.js; the consumer updates pressed state and target together. Selection paints above hover, both below labels. Idle hover is transparent at selected bounds; fresh hover moves/fades from there, and leave returns/fades to selection. See segmentedGeometry for Inset radii and [shared motion](../../apple-smooth-motion.md) for reduced-motion handling. Verify selected rest paint after moving focus away.

When editable source already contains the maintained implementation, retrieve a duplicate recipe only to resolve a missing seam or adaptation question. Keep exact contracts and runtime prerequisites available; do not load all demonstrations or historical reports to author one component. Reuse unchanged reads and distinguish static packet size from measured authoring overhead.

## Composition decisions before styling

- Geometry ownership: use card__root, page__flow, section__flow, flow__root, cluster__root and their density/spacing contexts before writing layout CSS. Use grid__root for task columns and declared flow contexts for gaps. Custom arrangement is appropriate only for an unmet layout need; it must not reapply card margin or replace composed radii with --r-margin. Radii derive from local n, the declared container role and the shared corner policy (k=1.5 for superellipse support, otherwise1); --r-* tokens include k once. Retired per-component corner knobs and radius presets do not alter them. Margins include borders, so CSS padding subtracts the border. Matching literals is not token consumption. Do not zero a maintained owner’s margins/gaps to rebuild its anatomy.
- Tables: choose local horizontal scrolling with a labelled, keyboard-reachable scroll region and readable column minimums, or an explicit narrow-screen record representation retaining each value's header association. Preserve native table semantics when scrolling. Associate a persistent visible table__hint through aria-describedby; preserve local scrolling with hidden scrollbar chrome. Do not solve width by `word-break:break-all` or fragments of short status/priority words. Check actual words at 390px and enlarged text; absence of document overflow is insufficient.
- Selection/detail tasks: put chooser before detail in DOM and narrow-screen reading/focus order. Avoid CSS ordering that disagrees with the task. Keep selected context adjacent to its detail and consequential actions. For incident review/resolution follow collections.operationComposition: selected detail → evidence → bounded plan → Resolve inside one task group, in DOM and narrow reading order. Use collections recordSelection and record-choice__root for record buttons; update aria-pressed and detail together and verify paint after blur.
- Evidence/research tasks: group related claims into quiet collections, emphasize the selected claim rather than every card, and keep evidence/detail/plan visibly connected. Check task distance and scrolling independently of token compliance; do not force a specific desktop arrangement.
- Supporting text: use the foreground paired with the actual surface. Enabled help and readonly content are not disabled exceptions. Verify help, errors and open disclosures in light/dark states; require normal text contrast of at least 4.5:1, retaining measurement uncertainty near the threshold.

## Verify the authored result

Read generation warnings and unverified coverage. Missing mark anatomy is actionable; unknown custom geometry owners require inspection, not a claim that zero warnings means fidelity. Test Save/Start through real user clicks and keyboard activation in the chosen host; see [controller guidance](../prototype-runtime.md#user-activation-and-form-defaults). Inspect current-step paint and mobile order on the final artifact. Static lint does not prove these behaviors or contrast.

Top-level product pages use page__root page__flow: page__root owns the outer margin, page__flow owns section gaps. Do not put page__root on nested groups. Non-tabular selectable records use card-option geometry through button.record-choice__root, with title and metadata in separate slots; compact selectors inside td/th retain the control minimum height, 0.5u block/1.5u inline margins and control radius. Wrapping grows height; a choice-body does not add another margin. For staged collection tasks, read [the stepper workflow guide](workflow-patterns.md#focus-and-task-grouping): it owns post-render heading focus and catalogue/summary/action grouping.

For custom interactive controllers, `component-context.mjs --runtime` gives the supplied module-scope API contract without loading the catalog implementation. Use only listed helpers or explicitly owned recipe dependencies. Runtime startup is separate from final task acceptance.

For a complete task surface use a main.page__root.page__flow wrapper. Embedded examples do not add another page margin. A card is not a page wrapper. Use `assets/recipes/booking-composition.html` for explicit catalogue/summary gap ownership; retrieve the exact stepper demonstration for progress anatomy. Each checkbox remains input.checkbox__control inside its choice label; stepper__root alone does not create indicator/label/connector slots.

When evaluating kit consumption, deliver the authoritative foundations and wireframe stylesheet rather than substituting a simplified parallel palette or geometry ladder. Distinguish native-semantic behavior from actual system styling; preserve source identities and group feedback beside its owning field.

## Applying the retrieved anatomy

Use declared classes and modifiers from the selected record, not plausible aliases such as button-secondary__root. Keep a field's required marker in the same label text run; do not add a separate flex child merely for punctuation. Distinguish a task introduction from the current step instruction: repeat a heading only when it supplies new context. In review summaries, keep each value adjacent to its label and put save/session status outside that pair. Give Back and confirmation their declared action treatments rather than relying on identical default buttons. These are composition checks, not a prescribed layout.

For capped selections and conditional delivery fields, use the fields reservationRecipe. It demonstrates attempted-action validation, stable error IDs and retained note state. Keep required text/mark in one label span, unavailable options in disabled native choice anatomy, metadata in the body column, and actions/summary in declared flow groups. Do not depend on an unlinked stylesheet to supply anatomy.

For reservation generation or revision, route directly to fields.reservationRecipe before inventing a parallel controller or layout. Adapt its declared fields/actions; retain one page margin, plain fieldsets within the card, choice-body slots and label/value groups. Preserve a predecessor when revising; use the recipe to repair only the changed seam.

Keep scrollbar chrome hidden in menus, listboxes, cards and other scroll regions. Retain overflow:auto, keyboard/wheel/touch scrolling and scroll-into-view for active options; hiding a scrollbar must not clip content or remove a useful overflow hint.

## New families and rendered acceptance

Repeat family-to-contract mapping when a later feature introduces new components; the initial retrieval batch is not permanent coverage. Native details/summary requires the disclosure record, including dynamically created evidence panels. Use details.disclosure__root > summary + div.disclosure__body; put multi-part body content in a maintained flow. A list item containing a claim, explanation and disclosures needs its own inner flow; its parent list gap only separates list items.

Run the [rendered contract audit](../../rendered-audit.md) on the delivered application. Fix anatomy/margin findings, inspect gap findings, and retain scoped limitations. Capture expanded-state evidence before navigation or rerender replaces that state.

For nested cards and disclosures with prose, retrieve `references/reading-regions.md` and its maintained reading-region recipe. Use one outer `reading-flow__root` owner; inspect expanded narrow text measure, not only margin correctness.

For evidence comparisons, duration/uncertainty tracks or conserved quantity splits, discover `evidence-comparison`, `interval-timeline` and `allocation` records with component-context. Their optional pure renderers and validation mechanics live in `assets/recipes/review-patterns.js`; read `references/review-patterns.md` for ownership and assembly.

For final visual composition acceptance, use the [rubric index and review checklist](../../review/index.md). Record alignment, grouping, density and wrapping observations on the delivered artifact; zero audit findings do not establish those judgments.

Before adding labels or containers, apply the [design principles](../../review/principles.md): each visible element needs a distinct task, naming or grouping purpose. A single chooser usually needs one visible associated label, not an imperative heading repeating its field label.

For explicit light/dark selection, set document.documentElement.dataset.theme to light or dark. Maintained root CSS sets color-scheme so light-dark() tokens actually change; verify computed foreground/background as well as attribute state.

For full-window diagrams with floating search/player/inspector panels, retrieve [canvas overlays](../../canvas-overlays.md). Native popover coverage alone does not establish dragging, camera stability or unobscured evidence.

Listbox paint uses one outer border and borderless options with no separators. Selected options use the paired action fill and checkmark; unselected options have transparent fill and no trailing placeholder glyph. Preserve the option box and nested radius: a transparent border may reserve geometry, but only the diagnostic Box guides state draws option boundaries (use an inward outline so it does not change layout). Interactive implementations retain a visible keyboard focus indicator and use a separate hover fill; static recipes do not simulate behavior.

Listbox selected/hover backgrounds use the conditional border inset in [interaction states](../../interaction-states.md). Container margins protect the outline first; compact options subtract the remaining border overlap from their paint bounds and radius, never from hit targets.

For new pages, use the [modular stylesheet contract](../../page-styles.md): load styles/index.css, retain editable recipe files, and preserve their edits across HTML builds. The maintained `scripts/build-page.mjs` creates this structure once in a new consumer directory, extracting fragment style blocks into styles/pages/page.css and retaining an optional classic controller in runtime/controller.js. Edit the generated files in place; the scaffold refuses existing output directories. Do not use the portable single-file builder as the default for these modular pages.

When authoring diagnostic spec lists or explanatory sections, use the [heading/description/data layout](../../page-styles.md#heading-description-and-data-layout). Keep row anatomy consistent across measurements and formulas; use the shared geometry contract for compact sizing.

## Current Control anatomy takes precedence

Use [current geometry](../../geometry-spacing.md) for new buttons and control composition. Older compact, native and ladder examples are compatibility recipes, not permission to reuse their 2n wrappers. Icon/glyph wrappers are fixed3n squares and remain internal Control anatomy. Keep wrapper budgets, centering space, label edge padding and additional gaps separate. Omit missing media wrappers; add label edge padding only to exposed label sides: half the base budget per side for label-only buttons, full budget on a single exposed edge. Use portable assets/geometry/control.mjs for required geometry and issues; validate measured frames with resolvePercentageRadiusGroup. Generated documents must copy/import these modules explicitly when dynamic geometry validation is needed; the CSS-only build does not run that validator automatically.
