# Nested reading regions

Place `reading-flow__root` once on the outer padded card or region containing nested cards, notices and disclosures. It establishes an inline-size query container; use a block/grid item with available width, not an intrinsically sized popover. Do not add it to every nested surface. At content width <=32rem, descendants share the outer horizontal text rail: card, notice and disclosure inline borders/radii are removed, card/notice/summary/body inline padding is zero. Block padding, headings, native disclosure controls and flow gaps preserve hierarchy. Nested disclosures share outer boundary paint by default at every width; transparent descendant borders preserve space, and repeated summary dividers are omitted. An enclosing disclosure may explicitly opt into data-nested-boundary="framed" for independently meaningful groups. Wide regions retain standard 3u card and 2u disclosure geometry. This is a composition policy, not a new density or token engine.

Use `assets/recipes/reading-region.html`. Keep necessary independent cards and native disclosure anatomy; do not hide or truncate prose. Layout is container-responsive, including narrow desktop side panels. Repeated query roots defeat the shared rail; use one owner.

Rendered verification checks visible paragraphs in cards/disclosures and explicit `[data-prose]` blocks of >=80 characters. Required content width is min(24ch in the text font, outer reading-region content width), or outermost task-card content width without a region (page content width only when no card owns the prose). `PROSE_MEASURE` catches narrow columns even with correct individual margins and no overflow. This practical floor does not certify readability. Open all nested disclosures together, test narrow/wide and intermediate widths, and inspect screenshots. Short labels, closed content and non-prose widgets need task-specific verification.
