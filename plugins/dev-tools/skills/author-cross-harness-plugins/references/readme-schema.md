# README schema for a cross-harness plugin

Everything an operator needs lives in ONE file: the plugin's own `README.md`. A separate
INVENTORY/GETTING-STARTED doc splits the reader's path and goes stale independently — ruled
out live (adia-sdlc #87, owner direction 2026-09-01: "include the inventory in the README.md
file so everything is in one place").

## Required sections, in order

1. **Title + one-paragraph identity** — what the plugin is, in domain terms, one paragraph.
2. **Install** — BOTH harnesses, each as paste-ready commands:
   - Claude Code: `/plugin marketplace add <owner>/<repo>` + `/plugin install <plugin>@<marketplace>`,
     plus the non-interactive settings-pin JSON for CI checkouts.
   - Codex: `codex plugin marketplace add …` + `codex plugin add …` (two steps — registering the
     marketplace does not enable the plugin), plus the upgrade command
     (`codex plugin marketplace upgrade`) and the fresh-session note for surface detection.
   - Any post-install arming step (e.g. a `team-init`-class verifier) stated here, with what it
     verifies and the explicit note that it installs nothing itself.
3. **Getting started** — the first-session path (arm, then tour), then 4-6 typical-use worked
   examples from the OPERATOR's seat, each as "you type X → what happens → what you see at the
   end", under ~6 lines each, citing real skill names (greppable). Examples are drawn from the
   plugin's own journeys, never invented flows.
4. **Filing bugs and feature requests** — two halves, both explicit:
   - reports about work in the GOVERNED repo: the plugin's own intake doors (defect/feature/chore
     shape, what each captures, that they dedup and land on the ruled backend);
   - reports about the PLUGIN itself: the plugin repo's own tracker, its label set, and whether
     the plugin's own intake doors work there (they do when the repo self-governs).
5. **Inventory (generated block)** — the full member listing (skills, agents, hooks, scripts)
   grouped by domain phase, one line of purpose each, EMBEDDED in the README between explicit
   markers:
   `<!-- inventory:begin generated by scripts/make_inventory.py, v<version>, <date> -->` …
   `<!-- inventory:end -->`.
   A bundled generator script (with selftest) derives it from frontmatter/descriptions/hooks
   registration/script docstrings so it cannot hand-drift; regeneration replaces ONLY the marked
   block, so hand-edits outside it survive. Any in-session tour skill (an `onboarding`-class
   member) shares the same grouping/source so the two cannot diverge.
6. **Compendium / docs pointers** — where the design record lives and its reading order.
7. **Release ledger (footer)** — newest first, one dated entry per shipped version; the release
   gate's version-parity check reads the newest line.

## Rules

- The ONE entry file is the file people actually open first — in a marketplace repo that is
  the REPO-ROOT README (ruled by the owner after the operator surface first landed one level
  down, #95): root carries Install/Getting started/Filing/inventory; the plugin README slims to
  plugin-internal duty (compendium reading order, release ledger — kept there when the release
  gate reads that file's ledger) plus one pointer up. Each section lives in exactly one file.
- Counts stated in prose ("55 skills, 6 agents") are stale-context hazards: keep live counts
  inside the generated block only, or state them with the version they were true at.
- A README docs-check (G10-class) that requires every bundled script be mentioned is satisfied
  BY the generated inventory listing scripts with one-line purposes — feed the gate, don't
  duplicate for it.

## Amendment 2026-09-01 — dual generated outputs, and the command-only caveat

- The generated inventory may ship as TWO outputs from ONE collector pass (the sanctioned
  no-fork exception): the README's marker-fenced block plus a standalone INVENTORY.md with a
  "GENERATED FILE — DO NOT HAND-EDIT" banner naming the generator. The banner is a load-bearing
  tripwire on its own: the freshness check fails a banner-stripped file even when counts still
  match. One `check` verifies both outputs from one live walk; the gate covers both.
- The Install section's "start a fresh task if surfaces don't appear" advice MUST be scoped to
  model-invocable skills, with command-only members named as intentionally absent from the
  model catalog (see behavioral-fidelity.md §Command-only is invisible by design).
- Accepted trade-off to disclose, not fix: moving the script listing out of the plugin README
  regresses a README-mentions-every-script gate (G10-class) to WARN baseline — feeding that
  gate by duplicating content back would reintroduce the fork the schema exists to prevent.
