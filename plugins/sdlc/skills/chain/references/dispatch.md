# Dispatch detail

How /chain spawns, waits for, and records a role. The three dispatch steps are in the chain skill.

How to spawn depends on the session. Headless (`claude -p`, including `scripts/bench.sh`, which raises `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`): `prepare` prints `run_in_background: false` under `SDLC_HEADLESS=1`, so every spawn is foreground; wait for its result in the same turn and never end your turn while a role is running, because ending the turn ends the session and abandons the run. `hooks/block-background.sh` denies Bash `run_in_background` calls and denies any Agent call unless `run_in_background` is explicitly `false` (Agent runs in the background by default, so a missing field counts as background) and every Monitor call whenever `SDLC_ROLE` is set or `SDLC_HEADLESS=1`; bench.sh and fanout set `SDLC_HEADLESS=1`, and any other headless launcher (a dogfood script) must set `SDLC_HEADLESS=1` itself. In an interactive session: a role, or a bench task's full /chain, can take 15 to 30 minutes. `prepare` prints `run_in_background: true`; spawn, end the turn, and wait for the completion notification, which re-invokes the session. Never poll with `sleep`. Once notified, run `dispatch.py record`; the result is the file `<role>-<level>.md`, and you read it only when the status in the pointer needs action (fail, blocked, replan, no verdict). Claude: after `record`, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.py prune`, make each `TaskStop task_id=<name>` call it lists, then `prune --done <name>`; a finished sub-agent stays an idle teammate until stopped. In section 4, call `dispatch.py advance` once per builder or verifier completion instead: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.py advance <dispatch_file>` takes the same flags and stdin as `record` and does record, prune, `steps.py next` and the next prepare in one call: a non-zero record stops there with its exit code and prepares nothing; then it drops the recorded role from the prune queue and prints `TaskStop task_id=<name>`, runs `steps.py next` on the step dir, and for `build`, `rebuild`, `verify` or `reverify` prepares that role and prints its dispatch JSON (before a rebuild after a verifier fail it appends the verifier's `## For the next attempt` to the step handoff under `## Previous attempt` itself); any other action prints `stop: <action> <reason>` and prepares nothing, and a handoff outside a `step-<n>/` dir prints `next: <hint>`. Send the printed `TaskStop` call and the next `Agent` spawn in the same response.
