# Landing a sub-agent lane

Detail for the fanout skill's `## Sub-agent lanes` items 3 to 5.

## Verifier (levels L2 and L3)

Levels L2 and L3: when the solo reports `verify: needed`, take the level from `steps.py verifier-level <worktree>/<task dir>` (L2, or L3 for a size L4 or L5, merge, or security ticket or one whose criteria pin an exact label or string; the solo may have written criteria after prep) and run the verifier command prep printed (`dispatch.py prepare --solo-model <model> verifier <level> <worktree>/<task dir>/handoff.md`; the flag carries the solo's family because its worktree holds no `role solo` row), spawn its JSON, and run `dispatch.py advance` on its dispatch file once it reports (it records, prints `TaskStop task_id=<name>`, and prints `next: <hint>`, since a ticket verifier's handoff is not in a step dir; send that TaskStop with your next call). Commit nothing for it: `land` reads the verifier result from the worktree's records dir (`order.py records-dir <worktree>/<task dir>`) and copies it into the integration worktree. An external branch with no worktree delivers its verdict by committing the verifier result into the ticket folder with `git add -f`, and `land` untracks it in the close commit. One verifier per ticket: a fail goes back to the solo once through SendMessage by name, then the verifier runs once more. Claude: after a plain `record`, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.py prune`, make each `TaskStop task_id=<name>` call it lists, then `prune --done <name>`; a finished sub-agent stays an idle teammate until stopped.

## Land

`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py land <branch> --ticket <id> ...` (prep printed the exact command; in an interactive session run it as a background Bash call with `run_in_background: true`, so the session keeps dispatching while the merge lock orders the lands, and read the result at its completion notice) takes the finished branch through the locked merge, the gates, the vacuous-gate refusal, `tickets.py close` and the `close <id>` commit on the integration branch, then prints the report: every ticket landed so far, with its `Lane for <id>` line and the level line. The outcomes are `merged`; `no changes` (the sub-agent committed nothing; a second ticket of one lane whose commits the first land's merge carried is `merged` instead, closed with `commits carried by merge <sha>`, T-0721); `no verifier result` or `verifier fail` (levels L2 and L3) (a `verifier fail (held <owner>: ...)` lands once its owner runs `dispatch.py settle-held <verifier result> --by <owner> --evidence <repo-relative path>` and lands again, with no second verifier, T-0684); `red: <gate> rc=<n> (log <path>)` (the merge is reset; the line ends with `: <line>`, the last FAIL, Error, `not ok` or non-zero exit line of that gate log, when it has one, T-0768); `gate vacuous`; and `merge conflict` (SendMessage the sub-agent to merge the integration branch into its branch, then land again). A conflict only in the generated roadmap, router and mailbox files or `notes.md` is no `merge conflict`: land resolves it and `tickets.py roadmap` regenerates them inside the merge commit (T-0565). A repo whose parallel lanes append to the same shared files (fixtures, scenario lists) names them in `.sdlc/config` with `merge_union: <glob> [<glob>...]` lines: a conflict in a matching path is union-merged the same way, the land prints `union-merged: <paths>`, runs the optional `merge_union_gate: <cmd>` (one cheap syntax check, such as a type check) in the integration tree before the merge commit, resets the merge as `union gate red: <cmd>` when it exits non-zero, and runs the full `--gate` set even for a light-class merge (T-0683). A land gate that blocks the integration queues at `gate_lock.py run --priority 1`. Concurrent `land` calls are safe: they queue on `<lanes-dir>/merge.lock` and merge one at a time, so start each as its own background call and never poll with `pgrep`; `fanout.py queue` prints the holder (`landing`) and the waiting lands. The first land creates the integration branch and worktree and each later land reuses them. When `.sdlc/config` declares `merge_gate: light` and `light_scope: <glob>...` lines, pass the light set with `--light-gate "<cmd>"` beside the `--gate`s: a merge whose paths outside the ticket root all match a `light_scope` glob runs only the `--light-gate` set (the land prints `gate: light`), any other runs the `--gate` set (`gate: full (<reason>)`); `--light-gate` without the `merge_gate: light` line refuses with exit 2. Continue at step 4 (Report) and step 5 (Main) below.

## Gate worker caps

The gate lock exports `SDLC_GATE_WORKERS` to every gate, but a test runner reads it only if the gate command passes it. `fanout.py prep` prints `warning: gate runs <runner> with no worker cap; add <flag>=$SDLC_GATE_WORKERS` for each `--gate` and `--light-gate` that runs one of these without its flag (the exit code is unchanged); add the flag with `$SDLC_GATE_WORKERS` as the value:

| Runner | Flag |
|---|---|
| `node --test` | `--test-concurrency=$SDLC_GATE_WORKERS` |
| `vitest` | `--maxWorkers=$SDLC_GATE_WORKERS` (or `VITEST_MAX_WORKERS=$SDLC_GATE_WORKERS`) |
| `playwright` | `--workers=$SDLC_GATE_WORKERS` |
| `jest` | `--maxWorkers=$SDLC_GATE_WORKERS` |
| any runner (memory) | none to add: the lock stops a gate whose process tree passes `max_rss_mb` (default 25% of RAM) and exits 137 with `gate_lock: stopped <name>: process tree RSS ... over max_rss_mb ...`; `gate_lock.py policy set max_rss_mb=N` changes it, `0` turns it off (T-0716) |

## Roll

A lane that `board.py --lanes` shows as Merge `rolling` (verified, on a base main contains, touching no `hash_bound: <glob>` path that `.sdlc/config` declares for hash-bound and generated files) can skip the integration branch: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py roll <branch> --ticket <id> --gate "<cmd>"...` merges it in a scratch worktree at main's tip, gates it, closes the ticket, and fast-forwards main. Any other lane is `integration (<reason>)`, merges nothing, and goes through `land`; `main not advanced` means git refused the fast-forward in your checkout (a local change in the way) and main is untouched.

## Sync a running lane

After landing a ticket that touches `.agents/`, `AGENTS.md` or `.claude/`, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py sync --paths .agents/,AGENTS.md,.claude/ <lane>` on each running lane so it gets the new guidance as one commit. `fanout.py sync <lane> --gate "<cmd>"` (add `--regen "<cmd>"` when `.sdlc/config` declares `hash_bound:` files) brings a running lane level with its integration branch: generated and hash-bound files resolve without a hand merge, and `sync conflict: <paths>` (exit 2, nothing changed) names the real conflicts for an L2 builder.

## Full tickets in sub-agent mode

A `full` ticket is driven by the parent factory, not by a lane process: the parent dispatches each role of `/chain` as a sub-agent against the lane tree prep printed (`<lanes-dir>/<lane>` on branch `<integration>-<lane>`, made with the `lanes.py open` command prep prints on its `tree:` line; `land` closes that tree after the lane's last ticket merged). A sub-agent shares the parent's cwd and a Bash call resets it, so each brief carries a `Tree: <path>` line and tells the role to `cd <path> &&` in every Bash call and to edit only under that tree. The parent reads only `steps.py next` and the records: per role completion it calls `dispatch.py advance --agent-id <id> <dispatch_file>` with the completion notice figures and nothing on stdin (it records the way `dispatch.py record --agent-id <id>` does, reading the result from the sub-agent transcript; never extract the final message yourself), which records, prints the `TaskStop` and runs `steps.py next`, then prepares the next builder or verifier against the same tree (or prints `stop: <action> <reason>`); send the TaskStop and the next Agent spawn in the same response. After the chain it commits `<id>: <title>` in the tree and lands `<integration>-<lane>`; the lane runs no filer, and `land` closes the ticket. The headless factory per lane is the default of `run`, and on Claude needs `SDLC_CLAUDE_EXEC=1`.

The `lane red` stop (T-0766): `steps.py next` prints `lane red` instead of `inherited` when the step's recorded base-sha is not an ancestor of the into branch named by the lane record and no resync merge from into sits between the fork point and the base, so an earlier step of the lane committed the red; the factory replans and does not fix main first.

The blocked solo stop (T-0760): `dispatch.py advance` on a solo whose report starts `blocked` (or `solo blocked`) prints `stop: blocked <report>: <line>; answer or fix what it names, then rerun the solo` and prepares no verifier at any level.
