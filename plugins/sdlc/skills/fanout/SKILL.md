name: fanout
description: "Run ticket lanes in parallel: each lane is a git worktree whose tickets run one at a time through the lane `steps.py lane` picks (the `solo` agent for ticket levels L1 and L2, the headless /chain for the rest), merge into an integration branch behind gates, and close there. On the Claude host the parent can dispatch the lanes as isolated background sub-agents (`fanout.py prep` and `land`). Use when several ready tickets can run side by side."
argument-hint: "<lane>=<ids>... <lane>@<branch>=<ids>... [options]"

**Codex host:** Before following this workflow, read the Codex adapter at `${CLAUDE_PLUGIN_ROOT}/skills/sdlc/SKILL.md` and apply its tool, argument, path, and process translations. Claude Code follows the workflow below directly.

For every role launch, pass `--routing-reason` to `dispatch.py prepare` (Codex: `SDLC_ROUTING_REASON`) as the selected role/level rationale, including the recorded cause of any escalation or replan. Arguments: `$ARGUMENTS`

## Arguments

| Argument | Meaning | Default | Example |
|---|---|---|---|
| `<lane>=<ids>` | A lane: a worktree whose tickets run one at a time; ids are comma separated | - | `alpha=T-0101,T-0102` |
| `<lane>@<branch>=<ids>` | An external lane: a branch an outside agent owns, registered by an `external_branch: <branch>` line in `.sdlc/config` | - | `codex@feat-x=T-0103` |
| `--root DIR` | The dir holding the tickets | `.sdlc` | `--root .sdlc` |
| `--base REF` | The ref the integration branch starts from | `HEAD` | `--base main` |
| `--integration BRANCH` | The integration branch name | `fanout/<today>` | `--integration fanout/wave3` |
| `--lanes-dir DIR` | The dir holding the lane worktrees | `<worktree root>/fanout` | `--lanes-dir ../<repo>.worktrees/wave3` |
| `--gate CMD` | A gate command run on each merge; repeat it for more gates | the project check or test commands, added in step 1 | `--gate "scripts/check.sh"` |
| `--light-gate CMD` | A light-set gate; repeat it for more; needs a `merge_gate: light` line in `.sdlc/config` | none | `--light-gate "npm run lint"` |
| `--paths P,...` | With `sync`: copy only these paths from the integration branch into a running lane as one commit, no merge | none | `sync --paths .agents/,AGENTS.md,.claude/ fanout/wave3-a` |
| `--regen CMD` | With `sync`: regenerate the `hash_bound:` files after their conflicts took the integration side | none | `sync fanout/wave3-a --regen "npm run gen"` |
| `--rewrite-refs` | Rewrite files that cite a closed ticket folder to its `.NNNN-<slug>` path; added only when the user picks it in step 2 | off | `--rewrite-refs` |
| `--lane auto\|solo\|full` | The lane of every ticket; `auto` follows `steps.py lane` per ticket | `auto` | `--lane full` |
| `--max-lanes N` | The most lanes running at once | 4 | `--max-lanes 2` |
| `--forward` | With `settle`: first merge main into a diverged integration branch and gate it (step 6); without it `settle` only fast-forwards | off | `settle fanout/wave3 --forward` |
| `--catch-up` | With `settle`: merge main into the integration branch under the merge lock with the roadmap, router and notes files regenerated, and stop: no gates, main unmoved, the tree kept | off | `settle fanout/wave3 --catch-up` |
| `--force` | With `prep`: open every lane although the load is over the gate lock's max_load (else 1). With `settle --forward` or `--catch-up`: skip the running-role check, which otherwise refuses (exit 2) while a role runs against the integration branch | off | `settle fanout/wave3 --forward --force` |
| `queue` | Print the land order of the lanes dir: the `merge.lock` holder as `landing` (`stale holder` when its pid is dead), then each waiting `fanout.py land`, or `queue: empty`; takes `--lanes-dir` and `--integration` | - | `queue --lanes-dir ../<repo>.worktrees/wave3` |
| `--stagger SECS` | The seconds between lane starts | 20 | `--stagger 60` |

Run from the project root. `fanout.py` makes commits only inside the lanes dir (the lane and integration branches); it never touches main and never pushes. A lane that stops on any outcome other than `merged` keeps its dirty tree as a `wip(<id>): <outcome>` commit on the lane branch only. An integration worktree with uncommitted tracked changes is refused before the merge as `integration dirty: <path>`, except regenerable bookkeeping (roadmap, router, mailbox files, `notes.md`), which `land` commits as one `bookkeeping: <paths>` commit (T-0772). The dirty-before-sync stop and the full wording: `references/lane-lifecycle.md`.

Heavy checks: `fanout.py` runs each `--gate` through `gate_lock.py`, and a role inside a lane runs its heavy suites, browser tests, and the full `check.sh` through the same machine-wide queue: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/gate_lock.py" run -- <cmd>`.

Lane lifecycle (open, the archive ref on close, `lanes.py sweep`, `lane_ports`, `lane_setup`): `references/lane-lifecycle.md`.

Solo first: for each ticket `fanout.py` runs `steps.py lane` in the lane worktree and follows it: `solo` (ticket levels L1 and L2 by default) starts the `solo` agent, anything else keeps the headless factory running /chain; `--lane solo` or `--lane full` forces the choice. A ticket of level L2 needs one independent verifier with Verdict pass before any merge. Solo lanes start through `scripts/solo_run.py`, which checks the ticket budget first (the lane stops as `driver failed rc=4 (budget gate: budget.py ack)`). One run holds at most `--max-lanes` lanes (default 4), starts them `--stagger` seconds apart (default 20), and refuses overlapping planned scope unless `--allow-overlap`. Read `references/solo-lanes.md` before the first run: hosts, cost records, the vacuous-gate stop, and how many lanes to start.

Lanes live in `<worktree root>/fanout/<lane>` by default (`--lanes-dir` overrides). The worktree root is `wtroot.py root`, by default the sibling `../<repo>.worktrees/` outside the repo; the Lanes section of the plugin's `AGENTS.md` states the rule. An explicit `--lanes-dir` inside the tree must be in `.gitignore`, or preflight refuses with exit 2. Legacy lane roots: `references/lane-lifecycle.md`.

An external lane (`<lane>@<branch>=<ids>`) names a branch an outside agent owns: no driver, no worktree, merged `--no-ff` under the lock, gated, and closed on the integration branch. Rules and the `merge conflict` outcome: `references/lane-lifecycle.md`.

## Sub-agent lanes (Claude host)
`run` starts every lane as its own process and stays the headless default; on Claude it needs `SDLC_CLAUDE_EXEC=1` (T-0288, T-0361). In an interactive Claude session the parent factory can dispatch the lanes as background sub-agents in isolated worktrees instead, which an account switch (`/login`) does not kill. `fanout.py` keeps the deterministic parts as scripts; the parent only spawns. Codex keeps `run`.

1. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py prep <arguments> --gate "<cmd>"...` is this mode's dry run: the refusals of `run` (an uncommitted handoff, a planned-scope overlap, more lanes than `--max-lanes`, an unignored lanes dir) plus one: the host puts each sub-agent worktree under its own host-owned `.claude/worktrees/`, so that dir must be in `.gitignore`, or prep refuses with exit 2. It creates no branch or worktree; it writes each solo ticket's dispatch record and its host lane record (`host record: <path>`). Show its plan and ask as in step 2.
2. Spawn each ticket with the Agent tool from the dispatch JSON prep printed for it: `subagent_type` (`sdlc:solo-L1`, `solo-L2`, or `solo-L3`), `name` (`<id>-solo`), `description`, `model`, `prompt`, `run_in_background`, and `isolation: worktree`. At most `--max-lanes` lanes at once, `--stagger` seconds apart, and a lane's next ticket only after the previous one landed. The host names the branch and folder itself, `worktree-agent-<agent_id>` under the host-owned `.claude/worktrees/agent-<agent_id>` (observed 2026-10-07), not after the `name`: `land` resolves the printed name once `record --agent-id` ran. `land` treats any such branch as a solo lane. The host sandbox refuses the solo's git and writes outside its worktree, so the solo leaves its change uncommitted with its report in the worktree; `land` commits it as `<id>: <title>` (T-0740). Never poll: a finished sub-agent notifies the session.
3. Levels L2 and L3: when the solo reports `verify: needed`, run `dispatch.py advance` on the solo's dispatch file: it records the solo and prepares the ticket verifier at the level `steps.py verifier-level <worktree>/<task dir>` prints (the verifier command prep printed does the same by hand). A solo report that starts `blocked` makes `advance` print `stop: blocked <report>: <line>` and prepare nothing (T-0760): answer it and rerun the solo. A report that starts `already fixed:` makes `advance` print the close line with `--reason` and prepare no verifier (T-0810). Spawn the JSON, and run `dispatch.py advance` on the verifier's dispatch file once it reports: `next: close ...` on a pass, `stop: fail ...` on a fail. Commit nothing for it. One verifier per ticket: a fail goes back to the solo once through SendMessage by name, then the verifier runs once more. The `--solo-model` flag, external branches, and pruning: `references/land.md`.
4. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py land <branch> --ticket <id> ...` (prep printed the exact command; interactive: a background Bash call with `run_in_background: true`) takes the branch through the locked merge, the gates, `tickets.py close`, and the `close <id>` commit, then prints the report. Concurrent `land` calls are safe: they queue on `<lanes-dir>/merge.lock` and merge one at a time, so start each as its own background call and never poll with `pgrep`; `fanout.py queue` prints the holder (`landing`) and the waiting lands. A land gate that blocks the integration queues at `gate_lock.py run --priority 1`. The outcomes (`merged`, `no changes`, `no verifier result`, `verifier fail`, `red: <gate>`, `gate vacuous`, `merge conflict`) and what each needs, plus the `--light-gate` set: `references/land.md`. Continue at step 4 (Report) and step 5 (Main) below.
   After landing a ticket that touches `.agents/`, `AGENTS.md` or `.claude/`, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py sync --paths .agents/,AGENTS.md,.claude/ <lane>` on each running lane so it gets the new guidance as one commit. `fanout.py sync <lane>` brings a running lane level with its integration branch (`sync conflict: <paths>` exits 2, nothing changed): `references/land.md`.
   A lane that `board.py --lanes` shows as Merge `rolling` can skip the integration branch with `fanout.py roll`: `references/land.md`.
5. A `full` ticket is driven by the parent factory, not a lane process: it dispatches each role of `/chain` as a sub-agent against the lane tree prep printed (`<lanes-dir>/<lane>` on branch `<integration>-<lane>`), each brief carrying a `Tree: <path>` line, and per role completion calls `dispatch.py advance --agent-id <id> <dispatch_file>` and follows what it prints (`TaskStop`, the next spawn, or `stop: <action> <reason>`; a `stop: blocked` after a solo report means answer its question, nothing is verified). The parent then commits `<id>: <title>` in the tree and lands `<integration>-<lane>`; the lane runs no filer. Full wording and the `lane red` stop: `references/land.md`. The headless factory per lane is the default of `run`, and on Claude needs `SDLC_CLAUDE_EXEC=1`.

## 1. Dry run
Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py run <arguments> --gate "<cmd>"... --dry-run`, adding the project's own check or test commands (for example `scripts/check.sh` or the test command from its README, AGENTS.md, or CLAUDE.md) as `--gate`s unless the arguments already name gates, and the light set as `--light-gate`s only when `.sdlc/config` has a `merge_gate: light` line. Show the plan it prints; its `close:` line shows whether the repo is in numbered mode. A refusal (exit 2) stops here: show it and fix the arguments with the user.

## 2. Confirm
Ask with AskUserQuestion which lanes and gates to run. Recommended first: run as planned. Other choices: change the gates, change the lanes, cancel.

When the plan's `close:` line says `numbered folders`, also ask, as a separate AskUserQuestion choice, whether to add `--rewrite-refs`: it rewrites files that cite a closed ticket's folder to its `.NNNN-<slug>` path. Never add it unless the user picks it; step 3 runs with the flag only if they did. A `merged, close refused` outcome naming `--rewrite-refs` means a citing file blocked the close.

## 3. Run
Run the same command without `--dry-run`. A solo ticket takes minutes; a fanout that sends tickets through the full /chain can take hours. Headless (`claude -p`): run it in the foreground with the Bash tool's `timeout` at 3600000, do not use `run_in_background` there, and never end the turn while it runs, because that ends the session and abandons the lanes. Any headless launcher must set `SDLC_HEADLESS=1` itself (hook rules: `references/lane-lifecycle.md`). In an interactive session: run it with `run_in_background: true` and wait for the completion notification. Never poll with `sleep`. Ending the turn is safe there because the notification re-invokes the session.

## 4. Report
When notified, print `<lanes-dir>/report.md` verbatim, then `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/board.py --lanes --waiting "<one line on what is next>"` verbatim. That is the status output; do not restate it. An `inherited red: step-<n>: <tests>` outcome means those gate tests were already red on the base: fix main first; nothing from that ticket was merged. When `steps.py next` prints `lane red` instead, the inherited base is an earlier step of the lane that is off the into branch (T-0766): replan, do not fix main. Fanout's close is the plain form (no `--ticket`), so a lane files no follow-up ticket and every follow-up item lands in `notes.md` on the integration branch.

## 5. Main
Ask with AskUserQuestion. When every ticket merged, recommended first: bring the integration branch into main. The other choice: leave main as it is. When some ticket did not merge, recommend leaving main and name the lanes to inspect. After the user picks it, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py settle <integration> --forward --gate "<cmd>"...`: it fast-forwards main, and when the integration branch has diverged (main moved after it was cut) it first merges main into the branch, regenerates the roadmap and router files, unions `notes.md`, runs the gates at the new tip and fast-forwards only on green; a conflict outside those files exits 2 with nothing changed and comes to the user with its paths, never to a hand merge. Then it closes the integration tree (its archive ref first); when lanes are still open into it, it keeps the tree and prints `settled: main advanced; integration kept (lanes open: ...)` with exit 0 (T-0770), and any other close refusal prints `lane still open: <path> (<outcome>)` with exit 1. `fanout.py` never pushes, and moves main only by that fast-forward. If another sub-agent round follows, `prep` needs main on the remote: ask the user with AskUserQuestion (push now, or stop here) and never push unasked (`references/main.md`). To bring main's new tickets into the integration branch without settling, run `settle <integration> --catch-up`; merge main into an integration branch only with `settle --catch-up` or `settle --forward`, never a hand `git merge`.

When `.sdlc/config` has a `merge_gate: light` line, the main step runs `fanout.py cover <integration>` and then `fanout.py settle <integration> --require-covered` in place of that settle (`references/main.md`).

PR merge: the plugin ships no PR merge script; a project's own must keep two invariants: the head contains the base tip (`git merge-base --is-ancestor origin/main HEAD`) and the gates ran at that head (`gh pr checks <n> --watch --fail-fast`). Detail: `references/main.md`.

Then run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py sweep --apply`, which closes every other landed lane; a lane younger than `lane_min_age_hours` waits for a later sweep. Check the queue with `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/board.py --lanes` and `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py list --stale`: a `closable` row is a missed settle or sweep. Settle comes first because the sweep keeps a lane whose tip is only minutes old (its `recent` row).
