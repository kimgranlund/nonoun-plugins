name: fanout
description: "Run ticket lanes in parallel: each lane is a git worktree whose tickets run one at a time through the lane `steps.py lane` picks (the `solo` agent for ticket levels L1 and L2, the headless /chain for the rest), merge into an integration branch behind gates, and close there. On the Claude host the parent can dispatch the lanes as isolated background sub-agents (`fanout.py prep` and `land`). Use when several ready tickets can run side by side."
argument-hint: "<lane>=<ids>... <lane>@<branch>=<ids>... [options]"
allowed-tools: Bash(python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py:*), Bash(python3 ${CLAUDE_PLUGIN_ROOT}/scripts/board.py:*), Bash(python3 ${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py:*), Bash(git merge --ff-only:*), Read

**Codex host:** Before following this workflow, read the Codex adapter at `${CLAUDE_PLUGIN_ROOT}/skills/sdlc-lite/SKILL.md` and apply its tool, argument, path, and process translations. Claude Code follows the workflow below directly.

Arguments: `$ARGUMENTS`

## Arguments

| Argument | Meaning | Default | Example |
|---|---|---|---|
| `<lane>=<ids>` | A lane: a worktree whose tickets run one at a time; ids are comma separated | - | `alpha=T-0101,T-0102` |
| `<lane>@<branch>=<ids>` | An external lane: a branch an outside agent owns, registered by an `external_branch: <branch>` line in `.sdlc/config` | - | `codex@feat-x=T-0103` |
| `--root DIR` | The dir holding the tickets | `.sdlc` | `--root .sdlc` |
| `--base REF` | The ref the integration branch starts from | `HEAD` | `--base main` |
| `--integration BRANCH` | The integration branch name | `fanout/<today>` | `--integration fanout/wave3` |
| `--lanes-dir DIR` | The dir holding the lane worktrees | `<toplevel>/.worktrees/fanout` | `--lanes-dir .worktrees/wave3` |
| `--gate CMD` | A gate command run on each merge; repeat it for more gates | the project check or test commands, added in step 1 | `--gate "scripts/check.sh"` |
| `--light-gate CMD` | A light-set gate; repeat it for more; needs a `merge_gate: light` line in `.sdlc/config` | none | `--light-gate "npm run lint"` |
| `--rewrite-refs` | Rewrite files that cite a closed ticket folder to its `.NNNN-<slug>` path; added only when the user picks it in step 2 | off | `--rewrite-refs` |
| `--lane auto\|solo\|full` | The lane of every ticket; `auto` follows `steps.py lane` per ticket | `auto` | `--lane full` |
| `--max-lanes N` | The most lanes running at once | 4 | `--max-lanes 2` |
| `--stagger SECS` | The seconds between lane starts | 20 | `--stagger 60` |

Run from the project root. `fanout.py` makes commits only inside the lanes dir (the lane branches and the integration branch); it never touches main and never pushes. When a lane stops on a driver failure or any outcome other than `merged`, a dirty lane tree is committed as `wip(<id>): <outcome>` on the lane branch only (never merged). A tree already dirty before a ticket's sync is WIP-committed as `wip(<id>): dirty before sync` and that ticket stops with the outcome `dirty before sync`, never merged. An integration worktree with uncommitted tracked changes is refused before the merge with the outcome `integration dirty: <path>`; nothing is merged or reset, so the edit survives. Inspect a stopped lane's `wip(` commit on its lane branch.

Lane lifecycle: lanes open through `lanes.py`, which writes each lane's `.lane.json`. A lane whose tickets all merged is closed after its archive ref `refs/archive/<date>/<branch>` is written, so its tree and branch are gone and `lanes.py archive restore` brings the branch back. A stopped lane stays, and the report says `lane still open: <path> (<outcome>)`. The integration tree stays until main contains the integration branch. `run` and `prep` start with `lanes.py sweep --apply`, which closes every landed lane, unless `.sdlc/config` has `lane_sweep: off`. `roll` removes its scratch tree at the end of every roll. When `.sdlc/config` has `lane_ports: <lo>-<hi>`, each lane gets a port, and its driver and gates see it as `$SDLC_LANE_PORT`.

Solo first: for each ticket `fanout.py` runs `steps.py lane` in the lane worktree and follows it. `solo` (ticket levels L1 and L2 by default) starts the `solo` agent from a typed brief at the level's model and effort, in a headless session (Claude: `SDLC_ROLE=solo claude -p --agent sdlc-lite:solo`, refused without `SDLC_CLAUDE_EXEC=1`, so use `prep` and `land` sub-agent lanes or `--driver`; Codex: `sdlc-solo-l1` to `l3` through `codex_exec.py`). A ticket of level L2 then needs one independent batched verifier with Verdict pass, from the solo or else one fanout runs (verifier L2, or L3 for the tickets `steps.py verifier-level` names), before any merge. Anything else keeps the headless conductor running /chain (on Claude also needs `SDLC_CLAUDE_EXEC=1`). `--lane auto` (the default) follows the lane script; `--lane solo` or `--lane full` forces the choice, and the report lists each ticket's lane. Solo lanes start through `scripts/solo_run.py`, which checks the ticket's budget first (at 80 percent of `budget_usd` with no ack the lane stops as `driver failed rc=4 (budget gate: budget.py ack)` and nothing starts) and records the session's cost in the ticket's `runs.jsonl`, so the budget and the board meter Claude solo lanes only: a Codex solo lane records cost null, and a sub-agent lane's `prep` writes an unpriced `role solo` row that `fanout.py land --transcript <solo transcript jsonl>` prices (an estimate, per field, calibrated; T-0331), and a `full` lane starts a conductor session that writes no record. One run holds at most `--max-lanes` lanes (default 4; above 16 it also needs `--yes-many`), starts them `--stagger` seconds apart (default 20; your plan limit and merge conflicts are the real limits, not the machine), and refuses two tickets in different lanes whose planned scope overlaps unless `--allow-overlap`. The report names the real model per backend for each solo level (Codex reads `adapters/codex/models.json`), and a gate whose output shows it ran no tests (`Ran 0 tests`, `no tests ran`, pytest rc 5) stops the ticket as `gate vacuous` unless `--allow-empty-gate`. A good first run is up to 4 lanes (the default cap) of tickets that touch different files; raise `--max-lanes` only after watching your plan's limit use and the merge conflicts. The planned-scope overlap refusal reads only a ticket's `step-<n>/` handoffs, so it cannot fire for solo tickets (they have no steps); merge-time overlap still serializes them.

Lanes live in `<toplevel>/.worktrees/fanout/<lane>` by default (`--lanes-dir` overrides). `.worktrees/` must be in `.gitignore`; otherwise preflight refuses with exit 2 and says to add it, and an explicit `--lanes-dir` inside the tree must be ignored too. Caveat: `.gitignore` does not exclude `.worktrees/` from vitest, tsc, or file watchers, so exclude it in the project's own config; Node module resolution also walks up from a lane worktree into the main tree's `node_modules`.

An external lane (`<lane>@<branch>=<ids>`) names a branch an outside agent (for example Codex) owns, registered with an `external_branch: <branch>` line in `.sdlc/config`. Fanout runs no driver on it, creates no worktree and no `<integration>-<lane>` branch, and never writes that branch. It is merged `--no-ff` into the integration branch under the lock, gated, and its tickets are closed there; a second ticket on the same branch merges nothing new and skips the gates. A `merge conflict` outcome means the outside agent merges the integration branch on their side before the run is repeated. The lane shows in `report.md` but not in `board.py --lanes`, which lists worktrees.

## Sub-agent lanes (Claude host)
`run` starts every lane as its own process and stays the headless default; on Claude it needs `SDLC_CLAUDE_EXEC=1` (T-0288, T-0361). In an interactive Claude session the parent conductor can dispatch the lanes as background sub-agents in isolated worktrees instead, which an account switch (`/login`) does not kill. `fanout.py` keeps the deterministic parts as scripts; the parent only spawns. Codex keeps `run`.

1. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py prep <arguments> --gate "<cmd>"...` is this mode's dry run: the refusals of `run` (an uncommitted handoff, a planned-scope overlap, more lanes than `--max-lanes`, an unignored lanes dir) plus one: the host puts each sub-agent worktree under `.claude/worktrees/`, so that dir must be in `.gitignore`, and excluded from watchers like `.worktrees/`, or prep refuses with exit 2. It creates no branch or worktree; it writes each solo ticket's dispatch record and its host lane record (`host record: <path>`). Show its plan and ask as in step 2.
2. Spawn each ticket with the Agent tool from the dispatch JSON prep printed for it: `subagent_type` (`sdlc-lite:solo-L1`, `solo-L2`, or `solo-L3`), `name` (`<id>-solo`), `description`, `model`, `prompt`, `run_in_background`, and `isolation: worktree`. At most `--max-lanes` lanes at once, `--stagger` seconds apart, and a lane's next ticket only after the previous one landed. The host names the branch and folder itself, `worktree-agent-<agent_id>` under `.claude/worktrees/agent-<agent_id>` (observed 2026-10-07), not after the `name`: read the branch from the Agent result. `land` treats any such branch as a solo lane; the brief tells the solo to commit `<id>: <title>` there and never push. Never poll: a finished sub-agent notifies the session.
3. Levels L2 and L3: when the solo reports `verify: needed`, take the level from `steps.py verifier-level <worktree>/<task dir>` (L2, or L3 for a size L4 or L5, merge, or security ticket or one whose criteria pin an exact label or string; the solo may have written criteria after prep) and run the verifier command prep printed (`dispatch.py prepare --solo-model <model> verifier <level> <worktree>/<task dir>/handoff.md`; the flag carries the solo's family because its worktree holds no `role solo` row), spawn its JSON, and run `dispatch.py record`. Commit nothing for it: `land` reads the verifier result from the worktree's records dir (`order.py records-dir <worktree>/<task dir>`) and copies it into the integration worktree. An external branch with no worktree delivers its verdict by committing the verifier result into the ticket folder with `git add -f`, and `land` untracks it in the close commit. One verifier per ticket: a fail goes back to the solo once through SendMessage by name, then the verifier runs once more. Claude: after `record`, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.py prune`, make each `TaskStop task_id=<name>` call it lists, then `prune --done <name>`; a finished sub-agent stays an idle teammate until stopped.
4. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py land <branch> --ticket <id> ...` (prep printed the exact command; in an interactive session run it as a background Bash call with `run_in_background: true`, so the session keeps dispatching while the merge lock orders the lands, and read the result at its completion notice) takes the finished branch through the locked merge, the gates, the vacuous-gate refusal, `tickets.py close` and the `close <id>` commit on the integration branch, then prints the report: every ticket landed so far, with its `Lane for <id>` line and the level line. The outcomes are `merged`; `no changes` (the sub-agent committed nothing); `no verifier result` or `verifier fail` (levels L2 and L3); `red: <gate>` (the merge is reset); `gate vacuous`; and `merge conflict` (SendMessage the sub-agent to merge the integration branch into its branch, then land again). A land gate that blocks the integration queues at `gate_lock.py run --priority 1`. Land one branch at a time: the first land creates the integration branch and worktree and each later land reuses them. When `.sdlc/config` declares `merge_gate: light` and `light_scope: <glob>...` lines, pass the light set with `--light-gate "<cmd>"` beside the `--gate`s: a merge whose paths outside the ticket root all match a `light_scope` glob runs only the `--light-gate` set (the land prints `gate: light`), any other runs the `--gate` set (`gate: full (<reason>)`); `--light-gate` without the `merge_gate: light` line refuses with exit 2. Continue at step 4 (Report) and step 5 (Main) below.
   A lane that `board.py --lanes` shows as Merge `rolling` (verified, on a base main contains, touching no `hash_bound: <glob>` path that `.sdlc/config` declares for hash-bound and generated files) can skip the integration branch: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py roll <branch> --ticket <id> --gate "<cmd>"...` merges it in a scratch worktree at main's tip, gates it, closes the ticket, and fast-forwards main. Any other lane is `integration (<reason>)`, merges nothing, and goes through `land`; `main not advanced` means git refused the fast-forward in your checkout (a local change in the way) and main is untouched.
5. A `full` ticket is driven by the parent conductor, not by a lane process: the parent dispatches each role of `/chain` as a sub-agent against the lane tree prep printed (`<lanes-dir>/<lane>` on branch `<integration>-<lane>`, made with the `lanes.py open` command prep prints on its `tree:` line; `land` closes that tree after the lane's last ticket merged). A sub-agent shares the parent's cwd and a Bash call resets it, so each brief carries a `Tree: <path>` line and tells the role to `cd <path> &&` in every Bash call and to edit only under that tree. The parent reads only `steps.py next` and the records. After the chain it commits `<id>: <title>` in the tree and lands `<integration>-<lane>`; the lane runs no filer, and `land` closes the ticket. The headless conductor per lane is the default of `run`, and on Claude needs `SDLC_CLAUDE_EXEC=1`.

## 1. Dry run
Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py run <arguments> --gate "<cmd>"... --dry-run`, adding the project's own check or test commands (for example `scripts/check.sh` or the test command from its README, AGENTS.md, or CLAUDE.md) as `--gate`s unless the arguments already name gates, and the light set as `--light-gate`s only when `.sdlc/config` has a `merge_gate: light` line. Show the plan it prints; its `close:` line shows whether the repo is in numbered mode. A refusal (exit 2) stops here: show it and fix the arguments with the user.

## 2. Confirm
Ask with AskUserQuestion which lanes and gates to run. Recommended first: run as planned. Other choices: change the gates, change the lanes, cancel.

When the plan's `close:` line says `numbered folders`, also ask, as a separate AskUserQuestion choice, whether to add `--rewrite-refs`: it rewrites files that cite a closed ticket's folder to its `.NNNN-<slug>` path. Never add it unless the user picks it; step 3 runs with the flag only if they did. A `merged, close refused` outcome naming `--rewrite-refs` means a citing file blocked the close.

## 3. Run
Run the same command without `--dry-run`. A solo ticket takes minutes; a fanout that sends tickets through the full /chain can take hours. Headless (`claude -p`): run it in the foreground with the Bash tool's `timeout` at 3600000, do not use `run_in_background` there, and never end the turn while it runs, because that ends the session and abandons the lanes. `hooks/block-background.sh` denies Bash `run_in_background` calls and denies any Agent call unless `run_in_background` is explicitly `false` (Agent runs in the background by default, so a missing field counts as background) whenever `SDLC_ROLE` is set or `SDLC_HEADLESS=1`; bench.sh and fanout set `SDLC_HEADLESS=1`, and any other headless launcher (a dogfood script) must set `SDLC_HEADLESS=1` itself. In an interactive session: run it with `run_in_background: true` and wait for the completion notification. Never poll with `sleep`. Ending the turn is safe there because the notification re-invokes the session.

## 4. Report
When notified, print `<lanes-dir>/report.md` verbatim, then `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/board.py --lanes --waiting "<one line on what is next>"` verbatim. That is the status output; do not restate it. An `inherited red: step-<n>: <tests>` outcome means those gate tests were already red on the base: fix main first; nothing from that ticket was merged. Fanout's close is the plain form (no `--ticket`), so a lane files no follow-up ticket and every follow-up item lands in `notes.md` on the integration branch.

## 5. Main
Ask with AskUserQuestion. When every ticket merged, recommended first: bring the integration branch into main. The other choice: leave main as it is. When some ticket did not merge, recommend leaving main and name the lanes to inspect. After the user picks it, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py settle <integration> --forward --gate "<cmd>"...`: it fast-forwards main, and when the integration branch has diverged (main moved after it was cut) it first merges main into the branch, regenerates the roadmap and router files, unions `notes.md`, runs the gates at the new tip and fast-forwards only on green; a conflict outside those files exits 2 with nothing changed and comes to the user with its paths, never to a hand merge. Then it closes the integration tree (its archive ref first) and prints `lane still open: <path> (<outcome>)` with exit 1 when it cannot. Never push, and move main only by that fast-forward.

When `.sdlc/config` has a `merge_gate: light` line, light merges reached the integration branch behind the light set only, so the main step runs two commands in place of that settle, after the user picks it: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py cover <integration> --gate "<cmd>"...` runs the full gate set at the integration tip and commits a `gate-ledger.jsonl` entry (red prints a `git bisect start <to> <from> --first-parent` line: stop and show it), then `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py settle <integration> --require-covered`, which refuses (exit 2) an uncovered tip and otherwise performs the fast-forward and closes the integration tree as above.

PR merge: the plugin ships no PR merge script; a project's own must keep two invariants, and `settle --forward` keeps both for the local path. (a) The branch head contains the base tip before the merge (`git merge-base --is-ancestor origin/main HEAD`, by rebase or merge commit; never a squash of a branch cut before the last merge). (b) The gates ran at that head sha and none is pending (`gh pr checks <n> --watch --fail-fast` is the GitHub form; read-only).

Then run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py sweep --apply`, which closes every other landed lane; a lane younger than `lane_min_age_hours` waits for a later sweep. Check the queue with `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/board.py --lanes` and `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py list --stale`: a `closable` row is a missed settle or sweep. Settle comes first because the sweep keeps a lane whose tip is only minutes old (its `recent` row).
