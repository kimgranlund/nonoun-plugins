# Landing a sub-agent lane

Detail for the fanout skill's `## Sub-agent lanes` items 3 and 4.

## Verifier (levels L2 and L3)

Levels L2 and L3: when the solo reports `verify: needed`, take the level from `steps.py verifier-level <worktree>/<task dir>` (L2, or L3 for a size L4 or L5, merge, or security ticket or one whose criteria pin an exact label or string; the solo may have written criteria after prep) and run the verifier command prep printed (`dispatch.py prepare --solo-model <model> verifier <level> <worktree>/<task dir>/handoff.md`; the flag carries the solo's family because its worktree holds no `role solo` row), spawn its JSON, and run `dispatch.py advance` on its dispatch file once it reports (it records, prints `TaskStop task_id=<name>`, and prints `next: <hint>`, since a ticket verifier's handoff is not in a step dir; send that TaskStop with your next call). Commit nothing for it: `land` reads the verifier result from the worktree's records dir (`order.py records-dir <worktree>/<task dir>`) and copies it into the integration worktree. An external branch with no worktree delivers its verdict by committing the verifier result into the ticket folder with `git add -f`, and `land` untracks it in the close commit. One verifier per ticket: a fail goes back to the solo once through SendMessage by name, then the verifier runs once more. Claude: after a plain `record`, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.py prune`, make each `TaskStop task_id=<name>` call it lists, then `prune --done <name>`; a finished sub-agent stays an idle teammate until stopped.

## Land

`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/fanout.py land <branch> --ticket <id> ...` (prep printed the exact command; in an interactive session run it as a background Bash call with `run_in_background: true`, so the session keeps dispatching while the merge lock orders the lands, and read the result at its completion notice) takes the finished branch through the locked merge, the gates, the vacuous-gate refusal, `tickets.py close` and the `close <id>` commit on the integration branch, then prints the report: every ticket landed so far, with its `Lane for <id>` line and the level line. The outcomes are `merged`; `no changes` (the sub-agent committed nothing); `no verifier result` or `verifier fail` (levels L2 and L3); `red: <gate>` (the merge is reset); `gate vacuous`; and `merge conflict` (SendMessage the sub-agent to merge the integration branch into its branch, then land again). A conflict only in the generated roadmap, router and mailbox files or `notes.md` is no `merge conflict`: land resolves it and `tickets.py roadmap` regenerates them inside the merge commit (T-0565). A repo whose parallel lanes append to the same shared files (fixtures, scenario lists) names them in `.sdlc/config` with `merge_union: <glob> [<glob>...]` lines: a conflict in a matching path is union-merged the same way, the land prints `union-merged: <paths>`, runs the optional `merge_union_gate: <cmd>` (one cheap syntax check, such as a type check) in the integration tree before the merge commit, resets the merge as `union gate red: <cmd>` when it exits non-zero, and runs the full `--gate` set even for a light-class merge (T-0683). A land gate that blocks the integration queues at `gate_lock.py run --priority 1`. Land one branch at a time: the first land creates the integration branch and worktree and each later land reuses them. When `.sdlc/config` declares `merge_gate: light` and `light_scope: <glob>...` lines, pass the light set with `--light-gate "<cmd>"` beside the `--gate`s: a merge whose paths outside the ticket root all match a `light_scope` glob runs only the `--light-gate` set (the land prints `gate: light`), any other runs the `--gate` set (`gate: full (<reason>)`); `--light-gate` without the `merge_gate: light` line refuses with exit 2.
