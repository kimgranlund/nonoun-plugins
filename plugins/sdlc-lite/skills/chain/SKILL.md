How to spawn depends on the session. Headless (`claude -p`, including `scripts/bench.sh`, which raises `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`): `prepare` prints `run_in_background: false` under `SDLC_HEADLESS=1`, so every spawn is foreground; wait for its result in the same turn and never end your turn while a role is running, because ending the turn ends the session and abandons the run. `hooks/block-background.sh` denies Bash `run_in_background` calls and denies any Agent call unless `run_in_background` is explicitly `false` (Agent runs in the background by default, so a missing field counts as background) and every Monitor call whenever `SDLC_ROLE` is set or `SDLC_HEADLESS=1`; bench.sh and fanout set `SDLC_HEADLESS=1`, and any other headless launcher (a dogfood script) must set `SDLC_HEADLESS=1` itself. In an interactive session: a role, or a bench task's full /chain, can take 15 to 30 minutes. `prepare` prints `run_in_background: true`; spawn, end the turn, and wait for the completion notification, which re-invokes the session. Never poll with `sleep`. Once notified, run `dispatch.py record`, then read the result from `<role>-<level>.md`.

## Lean chain
A size S or M ticket can run as a lean chain: the same roles with one or two coarse steps.

Lean conditions (all hold): a size S or M ticket; planner L1 or L2; at most two steps, each at builder L1 to L3; no merge step; no replan; and the change stays within one nearest `AGENTS.md` owner, or one script and its tests, with no change to a contract other roles parse (role output sections, level tables, `steps.py`, `tickets.py` invariants, hooks).

The full chain is mandatory when any of these holds: any step at L4 or L5; an `unresolved:` assumption; the ticket changes role behavior, a runner invariant, a hook, or a check (its focused live run is still required); or a step touches shared generated state (roadmap, router, generated Codex agents) alongside other tickets in flight. A lean task that meets any of these is on the full chain from that point. Work already done stays valid.

What lean means: the planner follows the Coarse steps rule in `${CLAUDE_PLUGIN_ROOT}/agents/planner.md`. Plan review is for plans with an L4 or L5 step only (`steps.py review`); a lean plan has none, so the planner's open readiness concerns go to the builder as `## Notes`. Each step gets one verifier, and lean never skips a role that `steps.py review` or `steps.py next` asks for.

Close-out: the lean lane always runs the filer. Sections 5 and 6 apply unchanged, with no new `close` gate.

What the code computes: `steps.py lane <task dir>` prints `solo`, `lean`, or `full` from these conditions, one `reason:` line per deciding fact, and appends each result to the task's `skips.md`; `steps.py lint` warns on step and criterion counts.

## 1. Brief
Get or create `.sdlc/<task>/handoff.md`. If it lacks context a clean agent would need, ask the user before running anything.

## 2. Understand (only what the task needs)
- Vague or overloaded ask → the /clarify flow first (unattended mode when no person is present: name gaps, never block).
- Greenfield with most decisions unmade → the /grill flow, only when a person is present; unattended, stop and tell the user a grill is needed.
- Scoped but many parts, or cross-cutting → the /decompose flow with `--plan` after any architect run.
- Unfamiliar code location → scout L1.
- Code whose history matters (odd patterns, "why is this here") → archaeologist L1.
- Outside facts needed → researcher at the rubric level.
- Cross-cutting or unfamiliar design → architect L1.
All run on the task handoff; their outputs land in the task dir for the planner.

A /chain run under fanout that stops mid-step leaves its work as a `wip(<id>): <outcome>` commit that fanout.py makes on the lane branch. A plain /chain outside fanout commits nothing and never commits on main.

## 3. Plan
Run planner on the task handoff. Then run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/steps.py review .sdlc/<task>` and follow the action on its first line:
- `split` → run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/steps.py split .sdlc/<task>`, which writes each `step-<n>/handoff.md` from the newest planner file; never parse the plan by hand.
- `review L1` → dispatch plan-reviewer L1 on `.sdlc/<task>/handoff.md`, then `steps.py review` again. If `dispatch.py prepare` exits 2 with `specgate:` lines on stderr (Codex: `run.sh`), `specgate.py check` refused the plan before any spawn: append those lines under `## Plan review` and replan as for a `steps.py split` `plan defect` (below).
- `replan` → append to the task handoff's `## Plan review` (create it if missing, keep earlier entries) one line `plan review: replan: <result path>` and one `plan review: replan: <finding>` line per `## Findings` item of that result, rerun planner L3 on the task handoff, then `steps.py review` again (a replan is reviewed only when it holds an L4 or L5 step).
- `stop` → interactive: one AskUserQuestion carrying the reviewer's `## Missing decisions` (a `blocked` verdict), or whether to replan once more (a second `replan` verdict), or the plan's `unresolved:` assumption; unattended: stop the task and report the reason line.

`steps.py split` refuses a plan whose newest plan review says `replan` or `blocked`, so a rejected plan is never split. The count of `replan` reviews is per task dir: the second one stops. Only the user can lift a `replan` verdict (for example a review that faults a sound plan): on their say-so run `steps.py split .sdlc/<task> --override-review "<reason>"`, which records `review override: <review file>: <reason>` under `## Plan review` so later `split --only N` calls and `steps.py review` accept that review. A `blocked` verdict is never overridden, and a newer plan review ends the override. Unattended, a `replan` stays a stop.

If `steps.py split` refuses with `plan defect`, the plan is wrong, not the build: append the refusal text to the task handoff under a `## Plan review` heading (create it if missing, keep earlier entries), rerun planner L3 on the task handoff, and run `steps.py review` again (a replan is reviewed only when it holds an L4 or L5 step) before splitting. After the second such refusal for this task, stop and ask the user. The full split here executes no criteria. The same handling applies to the split in 4.2, including a refusal from `--only N` for a red guard or a guard that changed the work tree.

## 4. Build and verify, one step at a time, in order
Resume: a /chain run on a task that already has `step-<n>/` dirs first checks for stale attempts. On a step dir whose attempt is stale and needs explicit recovery (always on Codex native transport; see shared run operations at `${CLAUDE_PLUGIN_ROOT}/skills/handoff-format/run-operations.md`), run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.py recover .sdlc/<task>/step-<n>` (Codex: `run_lifecycle.py recover`; `dispatch.py status <step dir>` lists the attempts), then inspect that step's artifacts and the working tree. Then run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/steps.py resume .sdlc/<task>` and continue from the step dir on its first line, following the action on its second line as below (`replan` takes the 4.2 path; `done` alone means every step passed, so go to section 5). Never start from the newest or highest step dir. A task with a plan but no `step-<n>/` dir returns to section 3 (`steps.py review`).

After each builder run and each verifier run, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/steps.py next .sdlc/<task>/step-<n>` and follow the action on its first line: `build`, `rebuild`, or `bump` → builder at that level; `verify` or `reverify` → verifier at that level; `replan` → the 4.2 path; `resplit` (a builder blocked with Notes starting `stale lane:`, meaning merged prerequisites are missing from the lane and the plan is sound) → rebase the lane onto them, rename the step dir to `step-<n>.superseded-<k>` (next free k), run `steps.py split --only <n> .sdlc/<task>`, and rerun the builder; it is never a replan and costs no planner run; `swap` → run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/steps.py swap .sdlc/<task>/step-<n>`: exit 0 → append one line `swap applied: step <n>: <its stdout line>` to the task handoff's `## Plan review` (create it if missing, keep earlier entries) and run the builder at the level `next` printed (a rebuild: no `## Previous attempt`, never a bump, never counted toward "a second fail"); exit 1 → append its stderr to `## Plan review` and take the 4.2 replan path; `done` → next step; `stop` → ask the user; `inherited` → the gate was already red at the pre-build HEAD (builder Status `inherited red: <tests>`, or verifier Verdict `inherited red: <tests>` from the verifier's pre-build gate check): interactive, ask the user through AskUserQuestion (fix main first, rebuild once main is green, or stop); unattended, stop the task and report the inherited tests. It is never a fail, a rebuild, a bump, a replan, or a reverify, and never waives the gate. `invalid result: <path>: <reason>` (from `steps.py next`, `steps.py review`, or `steps.py resume`, and the same text in a `steps.py split` refusal) → the newest result does not match its `results.py` schema: interactive, report the line and ask the user; unattended, stop the task and report the line. It is never a rebuild, a reverify, a bump, or a replan. A nonzero exit → stop and report its stderr. `dispatch.py record` exits 3 (Codex: `run.sh` exits 3) when the result fails `results.py validate`; the result file still exists, so run `steps.py next` as usual. A missing or disallowed Status or Verdict is not an invalid result to `steps.py next`: it still routes through items 5 and 6. The rules below are the spec the script implements.

For each step:
1. builder at the step's `level:`.
2. builder Status blocked → skip the verifier (never verify a blocked build) and run planner L3 on the task handoff (replan; it writes a new `planner-L3[-k].md`), move each `step-<n>/` with n at or above the blocked step that already holds builder or verifier output to `step-<n>.superseded-<k>/` (first free k), then run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/steps.py split .sdlc/<task>` (optionally `--only N` for the steps being rewritten; `--only N` also runs that step's `(guard)` criteria against the current tree and refuses on a red guard or a guard that changed the work tree, a `plan defect` handled like the section 3 split refusal) to write the remaining step handoffs from the newest planner file (earlier plans stay in place; the script refuses a step dir that still holds builder or verifier output, so rename first), continue from the blocked step. One exception: a block only on a file outside the step's scope criterion takes the scope widening route in item 9. A blocked builder is never rerun at the same or a higher level and its step handoff never gets `## Previous attempt`; the replan reads the builder's Notes itself (a Notes line starting with `plan defect:` names the criterion to fix). A replanned step whose builder blocks again on the same finding (same criterion, same root cause) is a recurring finding: append a `recurring finding:` entry quoting both Notes to the task handoff's `## Plan review` before the replan.
3. verifier at the level the rubric derives from the build level.
4. Verdict fail → rebuild the same level once (it writes `builder-L<n>-<k>.md`, so earlier attempts stay for the rubric's "earlier builder-*.md with Status blocked" count), with the verifier's "For the next attempt" appended to the step handoff under `## Previous attempt`. Before a second fail bumps, check whether it is a recurring finding: same criterion and same root cause as the first fail's For the next attempt, after the rebuild addressed it. A recurring finding appends a `recurring finding:` entry quoting both notes to the task handoff's `## Plan review` and takes the 4.2 replan path (planner L3, supersede, split, continue from this step); no bump, no `## Previous attempt`, and it does not count toward a bump. Any other second fail → bump the builder one level and repeat. A fail at L5 → stop and ask the user. Exception: a fail whose `## For the next attempt` starts with `plan defect:` takes the 4.2 replan path (planner L3, supersede, split, continue from this step) unless `steps.py next` prints `swap`, which takes the swap route in item 8; either way it never rebuilds as a fail, never bumps a level, never adds `## Previous attempt`, and does not count toward "a second fail". Every other fail keeps the rule above.
5. A verifier result with no pass/fail `## Verdict` is "no verdict": `steps.py next` prints `reverify`. Rerun the verifier at the same level. It is never a fail, never counts toward "a second fail", and never adds `## Previous attempt`. A second consecutive no verdict at the same build → stop and ask the user.
6. A builder result with no done/blocked `## Status`: `steps.py next` prints `rebuild` at the same level. It is never a fail and never a bump, and a second in a row → stop and ask the user.
7. Builder Status `inherited red: <tests>`, or verifier Verdict `inherited red: <tests>`: the gate was already red at the pre-build HEAD, and `steps.py next` prints `inherited`. Interactive: ask the user through AskUserQuestion (fix main first, rebuild once main is green, or stop). Unattended: stop the task and report the inherited tests. It is never a fail, a rebuild, a bump, a replan, or a reverify, and never waives the gate.
8. Criterion swap: a verifier fail tagged `plan defect:` whose `## For the next attempt` holds exactly one `swap old:` line (the defective criterion's command span) and one `swap new:` line (the full replacement criterion) makes `steps.py next` print `swap L<build level>`. Run `steps.py swap` as in the action list above: it checks the pair, rewrites that one criterion line in the step handoff, and reruns the new spans against the built tree; never edit the criterion by hand. Exit 0 → append `swap applied: step <n>: <its stdout line>` to `## Plan review` and rebuild at the printed level, with no `## Previous attempt`, no bump, and no count toward "a second fail". Exit 1 (a refusal, whose last line starts `plan defect:`) → append its stderr to `## Plan review` and take the 4.2 replan path. A swap comes only from the verifier: a builder's `plan defect:` note always replans (item 2), because whoever writes the work never sets its check. One swap per step: a second swap proposal on the same step replans.
9. Scope widening: a builder blocked only because a file it needs sits outside the step's scope criterion, when the conductor decides the file serves the task goal (interactive runs confirm through AskUserQuestion). The decision is never recorded as prose alone. Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/steps.py widen .sdlc/<task>/step-<n> <path>...`. Exit 0 → append `scope widened: step <n>: <its stdout line>` to the task handoff's `## Plan review` (create it if missing, keep earlier entries), then run the builder at the blocked builder's level; that run is not a bump, gets no `## Previous attempt`, and the widened block does not count toward the rubric's blocked-builder bump. Exit 1 → append a `scope decision: step <n>: <paths>` line and the stderr to `## Plan review`, then take the 4.2 replan path. Why: the conductor names only paths and the script rewrites the check, so "never edit the criterion by hand" and "whoever writes the work never sets its check" both hold.

## 5. Loose ends
After the last planned step is `done`, finish small leftovers inside the task's Goal here, in this run, instead of filing them as tickets.
1. Dispatch filer L1 on `.sdlc/<task>/handoff.md`. This is the draft.
2. Collect the items inside the task's Goal: the draft's `fix-now:` Follow-ups, plus leftovers named in passed steps' builder `## Notes` and verifier results that a doc line, one test, a guard, or a one-file fix settles. Leave out anything that widens scope, needs a design choice, or needs the user; those stay `decide:` or `note:` follow-ups.
3. Nothing collected → section 6. Otherwise write `.sdlc/<task>/step-<n+1>/handoff.md` yourself (n = the last planned step) from the step template in handoff-format, titled `## Step <n+1>: Loose ends`, with `level:` the lowest fitting builder level (L1 or L2 as a rule), a `### Read first` subsection after `level:` and before `### Do` listing the nearest non-root `AGENTS.md` of each file the items change (the planner's rule; omit it when only the root applies), one Do line and one runnable criterion per item, each red now. Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/steps.py lint .sdlc/<task>/step-<n+1>/handoff.md` and fix any refusal. Never run `steps.py split` for this step.
4. Run the builder at that level, then `steps.py next` on the step dir for the verifier level, then the verifier. `done` → section 6. Any other outcome (verifier fail, no verdict, blocked builder, `inherited`) → one report line `loose end not finished: <item>: <reason>` naming the files the builder's `## Changes` lists, then section 6. It is never a rebuild, a bump, a replan, a swap, a `## Previous attempt`, or a question; the second filer run records it as a `note:` follow-up.

## 6. File
Run the /file flow on the task dir through its dry run and marks (steps 1 to 3.2). When a `Loose ends` step ran, its step 1 filer run is the second one (`filer-L1-2.md`, the newest by runs.jsonl, which close reads). When section 5 collected nothing, skip step 1 and reuse the draft. Hold the close (3.3 to 3.5) and the publish question (step 4) for section 7.

## 7. Close out
Run the /open-questions flow (`${CLAUDE_PLUGIN_ROOT}/skills/open-questions/SKILL.md`) on the task dir to collect what is still open. Drop items the /file questions below already cover.
- Interactive: make one AskUserQuestion call carrying the /file decide question (which `decide:` follow-up becomes the one ticket, 3.3), the /file publish question (step 4), and up to two open-questions items: at most 4 questions per call. Then close per /file 3.4 (`--ticket N --expect <digest>` when the user picked one), do only the publishing the user approved, and resolve the open items.
- Unattended (headless, no person present): never call AskUserQuestion. /file 3.5 decides the close, nothing is published, and the open items go in the final report as plain lines, or say nothing is open.

## Report
At every pause (after the plan, after each verdict, at the end) the whole status message is the /board render for this task: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/board.py --task <slug> --waiting "<line>"`, printed verbatim. Never a hand-made status table. Add only the task dir path at the end.
