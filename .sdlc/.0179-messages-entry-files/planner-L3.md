- `## Handle a message you were given`: numbered steps. The only code spans that start with `python3 ` in this section are exactly these three, in this order:
  1. `python3 "{{scripts}}/messages.py" read <path> --receiver <receiver>`. `<path>` is the path you were given. `<receiver>` is the folder after `new/`, which equals the message's `receiver:`. This moves the message to `read/`, stamps `read_time`, and prints it. Opening the file is not reading it: only `read` stamps `read_time`, and `ack` refuses a message without one. A path already under `read/<receiver>/` was claimed by a messenger, so skip this step.
  2. `python3 "{{scripts}}/messages.py" reply <id> "<reply text>"`. Only when `follow_up_requested: true`. `<id>` is the file name without `.md`.
  3. `python3 "{{scripts}}/messages.py" ack <id> --outcome "<outcome line>"`. This moves it to `done/` and stamps `ack_time`, so the stamps hold `send_time <= read_time <= ack_time`. It refuses a `follow_up_requested: true` message that has no reply.
- `## Send`: `python3 "{{scripts}}/messages.py" send --receiver <name> --sender <name> --topic "<one line>" --follow-up <true|false> "<body>"`.
  - Names match `[a-z0-9]+(-[a-z0-9]+)*`.
  - `--follow-up true` makes `ack` wait for a reply.
  - Optional flags: `--re <id>`, `--kind question|handoff|ack`, `--ttl` (default 7d).
  - A body of `-` is read from stdin. The command prints the new message path.
- `## Read`: `python3 "{{scripts}}/messages.py" count --receiver <name>`, `python3 "{{scripts}}/messages.py" list --receiver <name> --state new` (the id is the third tab-separated field), and `python3 "{{scripts}}/messages.py" read <id> --receiver <name>`. `read` prints the body between the BEGIN and END data markers.
- `## Reply`: `python3 "{{scripts}}/messages.py" reply <id> "<reply text>"` sends to the original's sender with the same topic and `re: <id>`. Add `--follow-up true` to ask for an answer back.
- `## Ack`: `python3 "{{scripts}}/messages.py" ack <id> --outcome "<outcome line>"`, after a reply when one was requested. A message never moves backward.
- `## Expire`: `python3 "{{scripts}}/messages.py" expire`. Outcomes are `expired`, or `expired, no reply` plus a notice to the sender.
- `## Messenger` (facts from `agents/messenger.md`, the `messenger` entry in `adapters/codex/models.json`, `adapters/codex/agents/sdlc-messenger-l1.toml`, and docs/codex-role-execution.md:9,27):

  - Parents send and reply through it, giving it the exact text.
  - It acks only when its parent asks. It never acks a `follow_up_requested: true` message before the parent replied.
  - Claude Code: the Agent tool with `subagent_type` `sdlc-lite:messenger` (model `claude-haiku-4-5`) and a prompt naming the harness `claude`, run in the foreground. Spawn it again to keep polling.
  - Codex: install the project agents once with `python3 "{{scripts}}/codex_roles.py" install .`. Then spawn the native agent `sdlc-messenger-l1` (model `gpt-5.6-terra`, effort low) with a prompt naming `codex`. Native agent calls need a fresh session after the install.

**`STAGE_TEMPLATES`, exactly these three lines each** (newline-terminated):

```
new:
`new/<receiver>/` holds messages sent to that receiver and not yet claimed; the full procedures are in `../AGENTS.md`.
A message leaves `new/` when its receiver claims it with `read` (it moves to `read/`) or when `expire` finds it past its `expires` time (it moves to `done/`).

read:
`read/<receiver>/` holds messages that receiver has claimed and not yet acknowledged; the full procedures are in `../AGENTS.md`.

Reply: `python3 "{{scripts}}/messages.py" reply <id> "<reply text>"`. Ack: `python3 "{{scripts}}/messages.py" ack <id> --outcome "<outcome line>"`.

done:
`done/<receiver>/` holds acknowledged or expired messages, with their `outcome` and, when acked, `ack_time`; the full procedures are in `../AGENTS.md`.
Nothing moves a message out of `done/`: a message never moves backward.
List them: `python3 "{{scripts}}/messages.py" list --state done`.
```

**Writer**
- `entry_files()` returns `[(relative path, bytes)]` for nine files:
  - `.gitignore` holding `*\n`.
  - `AGENTS.md`: the rendered `ENTRY_TEMPLATE`.
  - `CLAUDE.md` holding `@AGENTS.md\n`.
  - For each of `new`, `read`, `done`: `<stage>/AGENTS.md` (the rendered stage template) and `<stage>/CLAUDE.md` holding `@AGENTS.md\n`.
- Why the `.gitignore`: it makes the mailbox ignore itself. `git add -A` (fanout.py:586,684) and porcelain checks then never pick up entry files or messages, even in a repo that commits `.sdlc/` without ignoring `.sdlc/messages/`. A plan-time probe showed that a nested `.gitignore` holding `*` hides the folder from `git status --porcelain --untracked-files=all` and from `git add -A`.
- Why each `CLAUDE.md`: Claude Code loads a nested `AGENTS.md` only through a `CLAUDE.md` import (docs/reports/nested-entry-file-loading.md, Results for Claude Code).
- `write_entries(mbox)` creates folders as needed. For each entry file that is missing or whose bytes differ, it writes a temp file in the same folder and `os.replace`s it. It returns the paths written. It overwrites whole files, because they are generated, git-ignored, and not managed blocks.
- `cmd_send` and `cmd_reply` call `write_entries(mbox)` after `compose(...)` returns and before `deliver(...)`.
  - Every argument, body, and schema refusal is raised before that point, so a refused send or reply writes nothing. This keeps T-0177's contract: the selftest's `refused()` snapshots and the mailbox-absent checks at messages.py:1237 and 1267 keep holding.
  - `expire` does not write the entry files.
  - `list`, `count`, `read`, and `ack` already skip non-message entries: `receivers()` keeps only valid-name folders (messages.py:380-387).

## Risks
- Live arms are one trial each and can be flaky.
  - The Claude parent session in `claude -p` may end before the messenger reports.
  - A Codex native spawn from an untrusted temp project may not happen.
  - The probe reports these as fail or unverified. A Claude messenger fail blocks step 3 for a user decision, because the handoff requires that arm.
- The negative control may not bite if a role ignores the defective entry file and finds `messages.py` another way, for example by searching the disk. That would be a real finding about the claim, so step 3 blocks rather than weakening the oracle.
- The absolute script path in the generated files goes stale after a plugin upgrade until the next `send`, `reply`, or `roadmap`. The file names the `${CLAUDE_PLUGIN_ROOT}` and Codex fallbacks.
- Consumer repos gain a self-ignoring `.sdlc/messages/` holding nine entry files on every `roadmap`, `new`, or `close`. Every consumer router also goes stale once until `roadmap` reruns, as it does for any router template change.
- Other lanes changing tickets can make `.sdlc/AGENTS.md` stale again after step 2. Step 5 regenerates it.
- The Codex isolation proof depends on rollouts being named `rollout-*<thread_id>*.jsonl` under `$CODEX_HOME/sessions`, as observed on codex-cli 0.159.2.
- A conductor session cannot spawn the messenger until `block-role-spawn.sh` exempts it. That fix is out of scope here and is a follow-up.
