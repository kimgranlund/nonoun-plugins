1. CLI: `reorg.py apply PLAN [--root DIR] [--dry-run] [--approve DIGEST]` and `reorg.py selftest`. `--root` defaults to the Git top level of the current directory (inventory.py's `--root`). Exit 0 on success or a clean dry run, 1 on a refusal or a failed final check, 2 on a usage error.
2. Plan input (settles N1, N9, N15). A JSON file at any path, written from the session's plan; procedure Step 2 already puts that plan outside the repository (reorganization-plan-procedure.md:19). There is no plan ticket and no `onboard plan`, because N1 and N9 (reorganization.md:130, :135) show the ticket flow is broken. Shape: `{"version": 1, "batches": [{"name": str, "moves": [{"from": path, "to": path}], "links": [{"file": path, "old": target, "new": target}]}]}` with repo-relative paths. `links` is optional. A batch needs at least one move or one link fix. A wrong version, an unknown key, an empty name, or a wrong type is refused. Link fixes exist because the only applicable items in the one real plan (docs/reports/reorg-inventory-live-run/maison-plan.md, "Links to rewrite") are link retargets with no move. A link fix is matched against its file as the earlier batches left it (item 7).
3. Approval and digest. `--dry-run` runs every refusal except the approval, computes every batch on the in-memory tree (item 7), prints the listing and the digest, and writes nothing. The dry run never runs the final check: the check reads the real tree after each batch's writes (item 10), because its "existing path" clause needs the real tree, and the restore, baseline, and linkfix negative controls and the restore criterion below each need a digest from a dry run of a plan whose check will fail. Apply without `--dry-run` recomputes the same listing and digest before any write and needs `--approve DIGEST` equal to that digest; a missing value refuses, and a different one refuses with `reorg.py: refused: digest mismatch` at the start of the line. This replaces the draft's ticket status `ready` with the onboard precedent: dry run, show, ask once, then write (design.md:86). Digest: SHA-256 hex of the sorted lines `path <p>` for every tracked file outside `.sdlc/`, `file <p> <sha256 of the working-tree bytes>` for every tracked, non-frozen file outside `.sdlc/` (always including `docs/layout.md`), and `plan <json.dumps(plan, sort_keys=True, separators=(',', ':'))>`. `.sdlc/` is left out so changing run records never invalidates a plan (reorganization.md:75). The `plan` line makes a hand edit to the plan refuse (N15).

7. Citations and rewriting (settles N5). Forms: use `inventory.INLINE_LINK`, `REF_DEF`, `HTML_ATTR`, `MENTION`, `EXTERNAL`, `strip_fences`, `norm_target`, and `join_rel` (inventory.py:34-38, :60-88) and never redefine them, so inventory and apply share one definition of a link (inventory.py:15-21). Markdown means .md, .mdx, and .markdown. A Markdown line outside fenced code is a line `strip_fences` leaves unchanged; it keeps line numbers. Batches run in order on an in-memory copy of the tree: batch k reads every file as batches 1 to k-1 left it, moves and rewrites included. For batch k with move map M (`from` to `to`), go over every tracked, non-frozen file C that decodes as UTF-8; C lands at C' = M.get(C, C):
   - a. Claim spans line by line, first rule wins; a span one rule claimed is never examined by a later rule in this batch. In Markdown, outside fenced code: (1) link targets (group 1 of `INLINE_LINK`, `REF_DEF`, `HTML_ATTR`), skipping external and anchor-only targets; then (2) mentions (`MENTION`) that overlap no link span and resolve to a tracked path (c). Then in every file, anywhere, code and fences included: (3) repo-root path tokens equal to a `from` in M, found by rename_refs.py's `token_regex` and `in_url` (rename_refs.py:44-52), which T-0246 used across this repository.
   - b. Link target: t is `norm_target` of the text, and the suffix is the anchor and query after t. P is `join_rel` of t from C's folder before the batch (from the root for a leading `/`), whether or not P exists. When P is in M or C is in M, the new text is the relative path from the folder of C' to P' = M.get(P, P), plus the suffix; a leading `/` target becomes `/` + P', and a leading `./` is kept. So a moved file's broken links keep pointing at the same unresolved path.
   - c. Mention: P is the first of `join_rel(<C's folder>, t)` and `join_rel('', t)` that names a tracked path in the tree before the batch (inventory's order, inventory.py:207-213); a mention that names none is plain text and stays. A mention found through C's folder is relative: when P is in M or C is in M, it becomes the relative path from the folder of C' to P'. A mention found only through the root is a repo-root mention: when P is in M, it becomes P'. A mention with no `/` whose name is `AGENTS.md`, `CLAUDE.md`, or `README.md` is not a citation and stays: in prose it names a kind of file (docs/claude-response.md:55 means the plugin root's `CLAUDE.md` and would otherwise become `../CLAUDE.md`), and entry files never move (item 6).
   - d. Token: the token becomes its `to`. This is the only rule in non-Markdown files and in fenced code.
   - e. The target of every rewrite is P', the target's place after this batch, never its place before. Same batch: docs/plugin-compatibility.md:9 links `codex-role-execution.md`, and both files move to `docs/references/` in batch `references`, so the folder of C' and P' match and the link stays `codex-role-execution.md` with no listing line. Across batches the same occurrence is examined again, at most once per batch: docs/claude-response.md:60 mentions `codex-role-execution.md`; batch `references` rewrites it to `references/codex-role-execution.md`, and batch `other`, which moves the citing file to `docs/other/`, rewrites it to `../references/codex-role-execution.md`.
   - f. A citation the script cannot rewrite refuses and names the file and line (procedure step 3.3, reorganization-plan-procedure.md:41): a link target or mention inside fenced code of a non-frozen Markdown file that resolves from C's folder to a `from` in M; a mention in a non-Markdown file that resolves from C's folder to a `from` in M; and a non-UTF-8 tracked non-frozen file that contains the bytes of a `from`. Text equal to the repo-root path `from` is always the token case (d), never a refusal, even in a file at the repository root. Other fenced code stays as it is, even in a moved file.
   - g. A citation inside a frozen file is accepted and left byte-identical (reorganization.md:48). Matching is by resolved path, so a target naming a different file with the same name is never touched. A relative target that resolves above the repository root (`join_rel` returns None) stays unchanged.
8. Managed blocks. Rewriting a link inside an onboard managed block would make `onboard.py check` call it edited (design.md:113), and setup would then never refresh it, which the draft's last apply step relies on (reorganization.md:90). So when a rewrite changes the body of a block found by `onboard.find_block` (onboard.py:741) whose stored hash equals `onboard.digest` of the body before the rewrite, set the start marker to `onboard.START_MARKER` with the block's own version and `onboard.digest` of the new body. A block already edited by hand keeps its hash.
9. Running check: before any write, take a non-blocking exclusive `fcntl.flock` on every `.run.lock` under the root (the lock run_lifecycle.py:29-31 takes) and release each one right after. Skip `.git/` and every nested folder that holds its own `.git` entry, because that is another work tree (this lane itself sits under the main checkout's `.worktrees/`). A lock that cannot be taken refuses. A file that exists but is not held never refuses.
10. Apply, commit, check, restore (settles N8). One commit per batch follows the handoff and procedure step 3.4 (reorganization-plan-procedure.md:42) over the draft's "the user ... commits" (reorganization.md:90). Record the start HEAD S. Per batch: `git mv` each move (create parent folders), write the link fixes, rewrites, and managed-block hash refreshes the in-memory batch computed, run the final check on the real tree, then stage exactly the batch's paths and run `git commit` with the subject `reorg: <name>` and a body of `move <from> -> <to>` lines plus `plan digest <hex>`.
    - Final check: every link (`INLINE_LINK`, `REF_DEF`, `HTML_ATTR`, outside fenced code) in every tracked non-frozen Markdown file resolves to a tracked path, a folder holding tracked paths, or an existing path, except baseline entries; mentions are not checked, because a mention that names no tracked path is plain text (inventory.py:16). No tracked non-frozen file still holds a repo-root path token of a moved `from`, found by the same `token_regex` and `in_url` as item 7 d, so a token inside a URL is skipped by both. Every tracked frozen file outside `.sdlc/` has the content hash it had at the start (`.sdlc/` is left out because other runs write there).
    - Baseline: the broken links before the first batch, keyed by (file at the start, resolved target), or by the raw text for a target above the root. A moved file's key follows its move. The draft's key `{file, line, target}` would break when a rewrite shifts lines.
    - Restore: on any failure after the first write (a git error, a write error, a commit hook, a failed check), HEAD returns to S, every path the apply touched gets its S content and index entry, folders the apply created and left empty are removed, and files the apply did not touch stay byte-identical, including unrelated uncommitted changes and untracked files. Then exit 1.
11. Selftest: fixture repositories in temp dirs (a Git identity set per fixture), no model call, no network. Negative controls are in-process variants passed to gate functions, in onboard.py's `gate_*(impl)` style (onboard.py:1006). No CLI flag or environment variable disables a gate, unlike inventory.py's `SELFTEST_ESCAPES`. Print `ok <gate> positive` and `ok <gate> negative` per gate and `FAIL <gate> <case>: <reason>` per failure, and end with the line `reorg selftest: PASS` or `reorg selftest: FAIL` (exit 0 or 1). The gates follow the draft table (reorganization.md:112-122). Its Classification row is left out because a session now writes the plan (reorganization-plan-procedure.md:5):
    - `digest`: positive: an unchanged fixture applies, and a change under `.sdlc/` after the dry run leaves the digest the same. Negative: An edited document and an edited plan each refuse.
    - `approve`: positive: a matching `--approve` applies. Negative: No `--approve` refuses and writes nothing.
    - `frozen`: positive: a layout-listed frozen file that cites a moved file stays byte-identical and the apply passes. Negative: A source under `.sdlc/`, a listed frozen source, an ignored source, and a frozen destination each refuse.
    - `rewrite`: positive: an inline link, a reference definition, an HTML `href`, a root token in a non-Markdown file, a bare mention, a backticked mention, a repo-root mention, and the moved file's own links are rewritten, with anchors kept. Negative: A link and a mention that name a different file with the same name are unchanged, and a bare `CLAUDE.md` mention in a moved file is unchanged.
    - `batches`: positive: two files that link each other move together into one folder and print no rewrite line, and a third file that cites both is rewritten in batch one and again in batch two when it moves (the same-batch criterion's fixture below). Negative: A variant that rewrites to the target's place before the batch, and a variant that skips an occurrence already rewritten in an earlier batch, each fail the final check.
    - `citation`: positive: a citation in a frozen file does not refuse. Negative: A relative link to the moved file inside a fenced block refuses and names the file and line.
    - `baseline`: positive: a fixture with one link that was already broken applies and passes. Negative: A variant that skips one rewrite fails the final check.
    - `running`: positive: an unheld `.run.lock`, and a held one inside a nested work tree, do not refuse. Negative: A `.run.lock` held by a child process refuses.
    - `collision`: positive: a free destination applies. Negative: An existing destination, a case-only difference from a tracked path and from an untracked path, two moves to one destination, and an entry-file source each refuse.
    - `dirty`: positive: an unrelated modified file does not refuse and is byte-identical after the apply. Negative: A modified touched file and a staged change each refuse.
    - `restore`: positive: a passing apply leaves the moves committed. Negative: A failing check in batch two leaves HEAD at the start, the touched paths as before, the unrelated modified file byte-identical, and no created folder.
    - `commit`: positive: a two-batch plan makes exactly two commits with the subjects `reorg: <name>`, each holding only its batch's paths. Negative: A variant that commits both batches at once is caught.
    - `dryrun`: positive: the dry run prints every move, every rewrite, and the digest. Negative: A variant that writes during the dry run is caught by comparing the tree and HEAD.
    - `managed`: positive: an unedited managed block whose link is rewritten is not labeled edited by onboard's check. Negative: A variant without the hash refresh is labeled edited, and a hand-edited block keeps its old hash.
    - `linkfix`: positive: a fix retargets the matching link and the check passes. Negative: A fix whose `old` matches no link refuses, and a fix to a missing target passes the dry run, fails the check on apply, and restores.
