# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

A plugin marketplace (`sdlc-lite`, `.claude-plugin/marketplace.json`) holding one plugin, `sdlc-lite`, in `plugins/sdlc-lite/`. Paths below are relative to that plugin folder unless they start with the repo root. Git remote: `kimgranlund/sdlc-lite` (private). Raw role transcripts (`*.log`) and `bench/logs/` are gitignored; results `.md` and `runs.jsonl` are committed. All roles, skills, and systems on the roadmap are built. Five benchmark tasks are in `bench/tasks/`; the first baseline ran 2026-09-24 (3 of 5 hidden checks passed, $37.13; both failures were task-spec gaps, since fixed).

## Commands

- Check everything: `scripts/check.sh` (the `merge-step` template guard in check.py, level tables in run.sh, level-rubric, and this file agree; every agent has a run.sh case; the tickets, board, steps, fanout, and run selftests; `hook-selftest.sh`; shellcheck; `claude plugin validate`). Run it after any change to a level, model, effort, or role. The validate warning about this CLAUDE.md is expected: it guides work on this repo and is not shipped as context.
- Load it in a session: `claude --plugin-dir /Users/kimba/Projects/nonoun/sdlc-agents/plugins/sdlc-lite`, then `/sdlc-lite:<skill>`. Or install from this repo as a marketplace (`/plugin marketplace add /Users/kimba/Projects/nonoun/sdlc-agents`).
- This repo's own sessions run as `sdlc-lite-author` (`.claude/agents/sdlc-lite-author.md`, set in `.claude/settings.json`): the maintainer's invariants, after-change checks, and learned hazards. Keep it in sync with this file.
- Default agent: in a target repo's `.claude/settings.json`, `"agent": "sdlc-lite:conductor"` makes every session there the conductor (routes asks to skills, dispatches roles, reports with /board, makes only trivial edits itself). Declare it per repo, never in user settings.
- Run one role directly: `scripts/run.sh <role> <level> <handoff.md>` (writes `<role>-<level>.md`, `.log`, and a `runs.jsonl` line next to the handoff; a rerun writes `<role>-<level>-<k>.md` and never overwrites)
- Check a level mapping without a model call: `SDLC_DRY_RUN=1 scripts/run.sh builder L3 <handoff.md>`
- Fan out lanes: `scripts/fanout.py run <lane>=<ids>...` (skill `/fanout`: dry run, confirm, run, report, then an optional `git merge --ff-only` of main after approval).
- Benchmark: `scripts/bench.sh [task ...]` runs tasks headless (raises Bash timeouts so role runs stay in the foreground), then `scripts/bench-summary.sh`. The bench dir (tasks, results, logs) resolves in this order: `--bench-dir DIR`, then `SDLC_BENCH_DIR`, then `<project>/bench/` (git toplevel), then the plugin's `bench/`, via `scripts/bench-dir.sh`. This repo's root has no `bench/`, so the dev bench stays at `plugins/sdlc-lite/bench/`.

## Layout

- `scripts/run.sh`: the one runner. Holds the role:level → model/effort table, a git preflight (exits 2 outside a git work tree or before the first commit), the Fable-never-verifies-Fable swap, and read-only enforcement (Edit/Write disallowed for every role except builder). Read-only does not block Bash, so the verifier's no-git-state-changes rule lives in its prompt.
- `hooks/block-publish.sh`: PreToolUse(Bash) hook. Inside a role run (`SDLC_ROLE`, set by run.sh per role run and by fanout for lane drivers) it blocks `git push`, `gh pr/issue` writes, `gh release`, mutating `gh api`, and package publishing. Your own session is not affected, so `/file` can publish after approval.
- `hooks/block-background.sh`: PreToolUse(Bash) hook. In a headless session (`SDLC_ROLE` set by run.sh or fanout, or `SDLC_HEADLESS=1`) it denies any Bash call with `run_in_background: true` (exit 2) and tells the model to run in the foreground with the Bash timeout at 600000 or more and never end the turn while it runs, because ending the turn ends the session and abandons the work. Convention: every headless launcher sets `SDLC_HEADLESS=1`; bench.sh and fanout do, and any other (a dogfood script) must set it itself. Interactive sessions are not affected.
- Feed: `scripts/board.py` renders the status board from `.sdlc/` (skill `/board`; `/chain` reports with it); it adds ID and Ticket columns, read with `tickets.py`'s parser, when a rendered task has ticket front matter, and leaves off tasks whose ticket is `dropped` or `done` with no recorded step work, and renders a `done` ticket with no plan as a `closed` task row (and `--summary` line); by default (no `--sort`) it orders by ticket id when any rendered task has ticket front matter (unticketed tasks follow by recency) and by recency otherwise; `--sort id|name|recent` overrides, and `--sort recent` restores recency; its "· changed" cache lives in a per-user cache dir outside the repo (`SDLC_BOARD_STATE_DIR` overrides it), so `/board` writes nothing into the tree; it prints a one-line hint when a legacy `.sdlc/.board-state.json` is present (never deleted automatically, never in `--summary`). `board.py --lanes` instead prints one `| Lane | Branch | Board |` row per `git worktree list` entry (worktree basename, branch, and that worktree's `--summary` line of the same-relative root), exits 1 outside a git work tree, and leaves the default board unchanged. `scripts/statusline.sh` shows line 1: model, dir, git (branch, dirty, ahead/behind, worktree), context % (🟡 at 70, 🔴 at 85), session cost and duration; line 2 only when `.sdlc/` has tasks: the live role run plus `board.py --summary` (task %, 🔴 count, ⚠ L5); it is wired in `~/.claude/settings.json` by absolute path to `plugins/sdlc-lite/scripts/statusline.sh` (backup: `settings.json.bak-statusline`). `output-styles/sdlc-feed.md` is an optional session style (`/output-style`). `run.sh` keeps `<role>-<level>.running` during a run so both can see live work.
- Agent skills: an agent's frontmatter `skills:` list is loaded by `run.sh` (appended with `--append-system-prompt-file`, plugin paths filled in), because `claude --agent` does not preload them (token probe with a positive control, 2026-09-24). planner ← `level-rubric`, architect ← `decompose`, verifier ← `checks-that-bite` (brought in from the user-level skill). `check.py` fails on a declared skill that does not exist.
- `scripts/tickets.py`: backs `/ticket`. `new <type> <slug> ["title"]` stamps a ticket with the next id, and `new` and `close` follow-ups take the next id above the max across the same-relative ticket root in every `git worktree list` tree (local root only outside git); `check` fails on two tickets sharing an id and names both folders, which also catches branches not checked out in any worktree after merge, `close <slug> [--force]` (run by `/file`; `close <slug> --reason "<text>"` closes a ticket finished by other work, without a filer file; `close <slug> --ack-warnings "<why>"` closes while Warnings are open, files follow-ups normally, and appends a `## Closed` section with the date, the reason, and the quoted warnings, refusing with `--force` or `--reason`, with empty text, or when no warnings are open, and with `--dry-run` passing the gate and writing nothing) sets the ticket `done`, files its filer follow-ups as `proposed` idea tickets, skipping any that exactly duplicate an existing ticket (normalized title or slug), and refuses while Warnings are open unless forced; a no-filer refusal names each other worktree's same-relative `<slug>/` folder holding a `filer-L*.md` (glob only, never read) so it can be committed or copied in; `close --dry-run` lists the proposed follow-ups with indices and duplicate marks, then one `open T-NNNN <title> [<slug>]` line per other proposed, ready, or blocked ticket, and writes nothing, ending with an `expect <digest>` line of the ordered follow-ups, and `close --skip N[,N...]` files all but the named ones, requires `--expect <digest>`, and refuses, writing nothing, when the digest no longer matches (`/file` runs the dry run and confirms the follow-ups first; none of these flags combines with `--reason`), `roadmap` regenerates `.sdlc/roadmap.md` in dependency order, `check` fails on a bad ticket or a stale roadmap, `selftest` proves each check failure fires. `--root DIR` sets the ticket root (default `.sdlc`). Numbered folders are opt-in: `--numbered` on `new`/`close`/`roadmap`/`check` or a `ticket_folders: numbered` line in `<root>/config` names folders `NNNN-<slug>` from the stamped id and makes `check` enforce the prefix only then, and `roadmap` refuses on a prefix mismatch in numbered mode; a successful `new --numbered` or `close --numbered` also persists that config line, so a later plain `check` enforces it, and plain `check` warns, without failing, when every folder has an `NNNN-` prefix but the config lacks the line; plain slugs are the default. In numbered mode `close` also renames `NNNN-<slug>` to `.NNNN-<slug>` so Finder and `ls` hide finished work; every tool treats a `.NNNN-<slug>` folder as a closed ticket in either mode (user decision, T-0054), `check` fails on a dot folder that is not done or dropped, and `archive [--dry-run]` renames existing done/dropped numbered folders; `_templates` and other dot entries stay skipped. Templates: `<root>/_templates/<type>.md` first, else `skills/ticket/templates/<type>.md`.
- `scripts/order.py`: the shared ordering rule for which result is newest (builder, verifier, planner): latest `runs.jsonl` record (run.sh records `file` on each line), else level then rerun index then name; never mtime. `check.sh` runs its selftest.
- `scripts/steps.py`: `split <planner.md | task dir> [--only N]` writes `step-<n>/handoff.md` per the step template, refuses a step dir holding builder or verifier output, refuses, with `plan defect` on stderr, a plan whose acceptance criterion command spans do not parse under `bash -n`, `lint <planner.md | task dir>` runs the same check and writes nothing, and `selftest` proves each failure; `/chain` steps 3 and 4.2 run it.
- `scripts/fanout.py`: `run <lane>=<id>[,<id>...]... [--root .sdlc] [--base REF] [--integration BRANCH] [--lanes-dir DIR] [--gate CMD]... [--driver CMD] [--dry-run]` runs ticket lanes in parallel. Each lane is a git worktree under the sibling `<toplevel>-fanout` (`--lanes-dir` overrides) on branch `<integration>-<lane>`, cut from the integration branch (`--integration`, default `fanout/<YYYY-MM-DD>`, created at `--base`, default `HEAD`, or reused), which is checked out in `<lanes-dir>/integration`. One thread and one headless conductor per lane (`claude -p --agent sdlc-lite:conductor`, Opus medium, told to run `/sdlc-lite:chain` unattended, run the filer without closing, and never commit, push, or publish); `--driver CMD` replaces it (stubs, the selftest) and gets `FANOUT_*` env, `SDLC_HEADLESS=1`, and `SDLC_ROLE=conductor`, so `hooks/block-publish.sh` guards the Claude sessions it launches. Per ticket, in order: sync the lane from the integration branch (under the lock, so a lane never picks up a merge still in its gates), run the driver, then the script makes the lane commit `<id>: <title>` (nothing staged: `no changes`). Under an exclusive `fcntl.flock` on `<lanes-dir>/merge.lock` (macOS has no `flock` binary) it merges the lane with `--no-ff` in the integration worktree, runs each `--gate` there, and on the first red one runs `git reset --hard` to the pre-merge commit; all green, it closes the ticket on the integration branch (`tickets.py close`, copying the lane's ticket folder in when the integration copy lacks a `filer-L*.md`) and commits `close <id>`. A lane stops at its first outcome other than `merged` and marks the rest `skipped`. It prints `[<lane>] <id> <event>` lines, writes and prints `<lanes-dir>/report.md`, and exits 0 only when every ticket merged, 1 otherwise, 2 on a refusal (preflight and `--dry-run` create nothing; unknown, done, or twice-listed ids, existing lane branches or dirs, and uncommitted handoffs refuse). Main is never touched: checkout, reset, and commit run only inside the lanes dir, nothing is pushed, and the worktrees stay for inspection. `selftest` proves it on throwaway repos with a stub driver; `check.sh` runs it.
- `agents/<role>.md`: one per role; each defines its output format as its final message, which the runner saves.
- `skills/level-rubric`, `skills/handoff-format`: reference skills (not commands) that the launcher skills and `/chain` read. The rubric must match the table in `run.sh`.
- Launcher skills: `/build`, `/plan`, `/verify`, `/research`, `/architect`, `/scout`, `/dig`, `/file`. Workflow skills: `/handoff`, `/chain`, `/bench`, `/board`, `/ticket`, `/fanout`. Understand skills (run in your session, not headless): `/clarify` (sharpen an ask into the handoff's Intent), `/grill` (greenfield decisions in question rounds, writes `design.md`), `/decompose` (two-plane breakdown, `coverage_check.py` gate, writes `decompose/`; the planner turns its leaves into steps). Modernized from harness find-intent, teamwork grill-the-ask, and harness break-down-problem.

## Decisions

- **Clean context is the default.** Agents start with no conversation history. Everything an agent needs arrives through its prompt, `$ARGUMENTS`, or a handoff file on disk (goal, decisions, paths).
- **Launch pattern: every role runs headless through the runner**, because only `claude -p --model --effort` can set effort (skill and agent frontmatter cannot). A skill with `context: fork` plus `agent:` is used only where effort does not matter.
- **Builders have 5 levels, each with a fixed model and effort:**

  | Level | Model | Effort |
  |---|---|---|
  | L1 | Sonnet | low |
  | L2 | Opus | low |
  | L3 | Opus | high |
  | L4 | Opus | xhigh |
  | L5 | Fable | xhigh |

- **Builders run headless, not as in-session subagents.** Agent and skill frontmatter have no `effort` field (checked against the docs on 2026-09-24), so every launcher skill calls `scripts/run.sh`, which runs `claude -p --agent sdlc-lite:<role> --model <m> --effort <e>`. Input and output go through handoff files (see `skills/handoff-format`).
- **Researcher, Planner, and Verifier have L1 to L3:**

  | Role | L1 | L2 | L3 |
  |---|---|---|---|
  | Researcher | Sonnet medium | Opus medium | Opus high |
  | Planner | Sonnet medium | Opus medium | Fable xhigh |
  | Verifier | Sonnet medium | Fable medium | Fable xhigh |

  Verifier level follows build level: builder L1 or L2 → verifier L1, L3 → L2, L4 or L5 → L3. A replan forces Planner L3. `run.sh` never lets a verifier run on the build's model family (user decision, T-0005): after a Fable build a Fable verifier becomes Opus at the same effort, and after a Sonnet build a Sonnet verifier becomes Opus medium.
- **Fable** is Builder L5, Verifier L2 and L3, Planner L3, and Architect. All models and efforts were confirmed by the user on 2026-09-24. There is no L6: when L5 fails, escalate to the user.
- **When `/build` gets no level**, the skill takes `level:` from the handoff if present. Otherwise it assesses the step against the rubric in `skills/level-rubric/SKILL.md` and picks the lowest fitting level. The same applies to every leveled role.
- **Headless runs use `--dangerously-skip-permissions`.** Every `claude -p` call includes it, so builders can edit files and run tests without prompts. (`auto` denied writes headless; `acceptEdits` needs allow rules for shell commands.) Run builders only in a repo or worktree you are willing to let them change.
- **A plan defect goes to a replan, never a rebuild.** The tag is the literal prefix `plan defect:`, emitted as the first line of a blocked builder's `## Notes`, the first line of a failing verifier's `## For the next attempt`, or the last line of a `steps.py split` refusal. `/chain` (and the conductor) answer it with a planner L3 replan on the task handoff, recording split refusals under the handoff's `## Plan review`; it never triggers a rebuild, a level bump, or a `## Previous attempt` note, and never counts toward a bump. The `steps.py split` lint (criterion command spans must parse under `bash -n`) is the one code gate; the rest is instructions. The planner runs each criterion once before writing it (red now for new behavior, green now for a `(guard)`), and scopes whole-file or repo checks to "no new findings versus the base commit". `check.py` guards the tag's presence across the docs (T-0060).
- **A full-context fork (`subagent_type: "fork"`) is an exception.** Use one only with a stated reason. It always runs on the parent's model and inherits the parent's blind spots, so it is never an independent reviewer.
- **A merge is a standard builder step.** The `merge-step` template lives in `agents/planner.md` and `skills/handoff-format/SKILL.md`. On a merge step the builder runs `git merge --no-ff <branch>` and makes the merge commit; that is the only step kind where the builder commits. Push and publishing stay blocked, and the verifier never changes git state. Its criteria are two parents, the branch as an ancestor, no MERGE_HEAD, no conflict markers in touched files, and gates with no new findings versus HEAD^1. `check.py` keeps the two copies identical and lint-clean, runs their conflict-marker guard against a throwaway repo, and keeps them in step with builder.md.
